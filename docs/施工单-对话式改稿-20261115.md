## 一、这份施工单要治什么

作者 2026-11-03 的判词是结构性的：墨坊的真身是**单发执行管线**（丢任务→跑批→出 Word），
**讨论余地不是没做好，是架构里没有这个构件**。

2026-11-03 补了“讨论构件”（`scripts/utils/discussion.py`）：讨论能落盘、能定稿成约束、
`stage4` 会把约束注入写作任务（`scripts/stage4_writing.py:896`）。这一步是通的。

但**讨论的 AI 那一边是空的**：

```
console/src/DiscussThreadPanel.vue:41
  <button class="mini" @click="say('ai')">以 AI 身份说</button>
```

点下去是**作者自己替 AI 打字**，`POST /discuss/say {role:"ai"}` 只是把一个字符串追加进 md
（`scripts/nf_api_domains/discuss_thread.py:89-106`）。于是“讨论”退化成“作者对着一个文本框自己跟自己
讲两遍”。

这份施工单补的就是这一段：**AI 真的能说、说的能变动作、动作由作者拍板、随时能叫停。**

## 三、多轮形态：为什么是内部会话体（决定项 4 的答复）

### 3.1 先拆一个容易混的地方

“内部会话体”和“踢一脚走一下”**不冲突**，因为它们说的是两件事：

| | 说的是什么 | 本项目的答案 |
|---|---|---|
| 会话体 | **存储与请求形状**：一轮轮消息存成 `messages[]` | 是，落 `session.json` |
| 踢一脚走一下 | **触发模型**：谁在什么时候发起一次模型调用 | 不变：一次触发 = 一次单发请求，不回环、不常驻 |

上游那一版把“常驻会话”也列进选项，其实混进来了第三种东西（长连接/后台循环）。
本项目不需要它，也不该要它——`AGENTS.md` 的整个成本模型建立在“一次 orchestrator.run() = 一个 run”
上，常驻会话会让成本与状态都失去边界。

所以答案是：**会话体做数据结构，单发做执行，两者叠着用。**

### 3.2 为什么不用“oneshot + 每次带前 N 轮讨论稿”

这是最省事的做法（把 md 全文塞进 user 消息），但有三个具体代价，都不是猜的：

1. **缓存会碎。** 讨论稿是**只追加的人读文档**：轮次头带时间戳
   （`discussion.py:append_round` 写 `### 第 N 轮 · 作者（2026-11-16T…）`），每次追加都会让
   整段前缀变化。压成文本再塞进去，逐字稳定区几乎为零 —— 与 `docs/agents/prompt-prefix.md`
   记的那次事故（前缀命中率上限 1.2%）是同一类病，只是换了个位置。
   `messages[]` 则是协议原生结构：固定 system + 追加历史，前面几轮逐字不动，缓存命中随轮次升高。
2. **没法裁剪。** 判据 1 要求讨论稿“只追加轮次，谁说了什么都留痕”（`discussion.py` 模块头）。
   要治长度（C11）就必须**另存一份可变的东西**。会话体天然就是那份东西：老轮次压成摘要、
   保留最近 K 轮原文，md 原文一个字都不动。
3. **结构化收口没地方挂。** 决定项 3 要 JSON。会话体的最后一轮就是“产出槽”，
   oneshot 则要从一大段文本里再解析一次，等于自己造一个更脆弱的分隔符。

### 3.3 落盘形状（写死，别自由发挥）

```
data/discuss/03/结局要不要开信.md          # 人读投影：只追加，永不改写（判据 1）
data/discuss/03/结局要不要开信.json        # 机读状态：status / constraints / decided_at（已有）
data/discuss/03/结局要不要开信.session.json # 模型读真源：messages[] + 摘要锚点 + 记账维度（新增）
```

三条纪律：

- **md 不是 session 的导出物，反过来才对。** md 是作者与 AI 共用的公开记录；session 是“给模型看的
  那份视图”。两者由同一次 AI 轮写入同一事件，但**禁止互相覆盖**。
- **压缩只动 session。** 压缩时把被压掉的轮次号记进 `archived_rounds: [1..k]`，摘要段注明
  “第 1–k 轮摘要（原文见 .md）”。任何时刻都能顺着轮次号回 md 查原文。
- **作者发言也要在 session 里。** 否则模型只看见自己说过的话，看不见作者怎么回的——
  那是“自问自答”，不是讨论。

### 3.4 会话前缀的稳定性（D3 的具体落法）

讨论轮有自己的请求，不走 `prompts/stage4_writing.md`。它的前缀纪律是：

```
[ 固定 ]  system：讨论规则 + 角色 + 输出 JSON 契约（逐字不变，改动视为破坏缓存）
[ 低频 ]  讨论背景：章号 / 主题 / 待解决问题 / 约束现状（开题时定，改主题才变）
[ 中频 ]  摘要锚点：被压掉的轮次摘要（压缩时变）
[ 可变 ]  最近 K 轮原文 messages
[ 产出 ]  本轮指令：这一轮要扮演谁、要产出什么字段
```

`K` 与 `摘要触发阈值` 都进配置（`config/system.yaml` 的 `discuss.*`），不写在代码里——
和 `chapter.target_words` 一样的处理方式。

### 5.1 C2 的 JSON 契约（写死）

```json
{
  "round": 7,
  "role": "ai",
  "text": "这一轮要说的话（人读原文，同时进 .md）",
  "stance": "push | question | concede | summarize",
  "evidence": [
    {"kind": "quote", "chapter": 12, "quote": "原文里的一句话", "why": "它支持什么判断"},
    {"kind": "setting", "name": "设定条目名", "why": "…"},
    {"kind": "judge", "chapter": 12, "rule": "J07", "why": "…"}
  ],
  "decision": "这一轮想让作者定的事（一句话，可空）",
  "action": {
    "kind": "none | suggest_edit | rewrite_chapter | refine_paragraph",
    "target": {"chapter": 12, "para_index": 3, "para_hash": "…", "quote": "…"},
    "why": "为什么要改这里"
  },
  "needs_author": true
}
```

三条硬要求：

- `evidence` 不许空。**没有引文的判断一律不认**（沿用判定引擎“引句必须能命中原文”的口径，
  `docs/agents/judge-engine.md`）。引文命中校验放服务端，不信任模型自报。
- `action` 只是**建议**。`rewrite_chapter` 也**不许直进** `rewrite_queue`（`ask.py` 现在是直进的）——
  与拍板 #3“一律候选区 → 用户勾完 → 合成”冲突。作者点一次才排队。
- `round` 由服务端回填，不采信模型输出（否则重复轮次号会覆盖历史）。

## 八、风险与如实声明

1. **`direct` 通道受厂商限制。** 作者原话：“部分厂商限制，不方便用”。所以 C1 必须在没有可用 key 时
   **明确报错并指出换哪条通道**，不许静默失败——这正是 C3 存在的理由。
2. **`agent` 通道永远无法进自动化验收。** 它依赖用户机器上的 `hermes` CLI 与订阅状态；
   测试只能 stub。它的价值是“没有 key 也能用”，不是“可验收”。**不许把它写成主路径。**
3. **C18 的停止精度是“一个块”。** 流式按 1024 字节读，停止延迟上限 ≈ 一个块的到达间隔；
   已生成的 token 已经计费，界面上不许写“已取消，未扣费”。
4. **`book_pack`（C4）会显著变长提示词。** 它只用于讨论请求，不进 `stage4` 模板；
   如果要进，必须先过 D3 的缓存核算，不许“顺手加进去”。
5. **本文件不含任何实施代码。** 开工时按 C 编号逐条提交，一条一个 commit，
   判据与实现同一次提交落地（D5）。

**三条实施中修的坑（写在这里，别重踩）：**

1. **`append_session_turn` 必须无条件 save。** `append_round` 先写 md；第一次写 session 时
   `load_session` 会从 md 回填，回填结果已含刚写的那轮 → 幂等分支 return，于是 session
   从来没真正落过盘（每次读都在重新解析 md）。用例 Q1a 就是钉这条。
2. **作者自己按的停止不许报 failed。** `_notify_stream_done` 的判据是
   “`stopped` 且 `state=="ok"` → `done.status="stopped"`”；worker 返回 `False` 会让界面
   把“我按了停”显示成“系统失败”。
3. **流式预览不能直接摊 JSON。** 模型输出的是 `{"text": …}`，token 直接显示出来作者看到的是
   协议。前端 `previewHuman()` 抽 `text` 字段的已生成部分（抽不出退回原文）。
   真机验收第一版就是靠截图发现的——**只跑 HTTP 用例不会暴露这个**。
4. **agent 引擎停不下来，就得说出来。** `HermesClient` 只有 `_post_chat`（oneshot 子会话，
   整块返回），没有流式接口 → `/discuss/ai_turn` 返回 `stoppable: false`，界面明说
   “整块返回，等它说完”，不让作者对一个按不停的按钮产生期待。判据 Q5g + U 段。
5. **本机 8091 常被 Hermes 的文件服务占着。** 界面用例第一版用 8091 起静态服务，
   `http.server` 当场退出，而 `wait_url` 命中的是**别人的服务** → 页面根本不是墨坊，
   所有点击都在等一个不存在的按钮（表现是 30 秒超时）。现在默认 8097，且启动 1.2 秒后
   检查子进程是否已退出 —— 端口被占必须立刻 FAIL，不许静默用别人的页面。
