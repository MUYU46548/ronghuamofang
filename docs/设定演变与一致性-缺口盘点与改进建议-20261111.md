# 设定演变与一致性：四层防线缺口盘点与改进建议

日期：2026-11-11
状态：盘点稿，未排期
范围：只谈"能不能查出设定/时间线不一致"，不谈写作质量、UI、打包

## 一、缘起

一个真实样本（细节已虚构化处理）：某条设定描述一个特征的演变——早期机型外观上可见，后期机型收进皮下、只能靠专用设备识别。它在原作正文里有 5 处描写，其中：

- 位置写法三处一致、两处另一说（同一标识，一处写额头，另说写太阳穴）
- 取消时点一处说已完成、另一处仍在使用

**这类冲突用现有管线全流程跑一遍，一处也不会报红。** 不是因为提示词不好，而是四层防线各自缺一段：

| 层 | 该做什么 | 现状 |
|---|---|---|
| 输入层 | 把原作正文与知识库词条搬进设定集 | 原文进不来；词条只搬前 300 字 |
| 判据层 | 判断"两个值是否真冲突" | 只有二值事件可判，演变类属性无处存 |
| 执行层 | 让检查真的跑起来 | 分批切断上下文；self 引擎下不跑模型 |
| 制度层 | 设定改了就复检 | canon 未冻结时查不出；旧章不再复检 |

结论：**不是漏洞成千上万，是四层各缺一段，而且缺的位置互相掩盖**——上层没数据，下层就永远返回"无冲突"。

## 二、现场体检（一个真实工作区）

```
engine: self          gates.agent_mode: true
stage1-4: done        data/chapters/raw: 10 章
stage5: pending       data/chapters/checked: 0 章
canon.json            不存在
story_state.json      不存在
tombstones.json       不存在
merge_audit.json      不存在
setting.json          _meta.engine = "self"，vault_readonly = true
```

三套体检机制（canon 快照 / 素材冲突清单 / 一致性账本）在该工作区**一次都没通电**。这不是代码坏了——阶段停在第 4 章末、引擎为 self，两者叠加的必然结果。但它暴露一个真问题：**没有任何地方会告诉作者"你的这些检查一项都没做"**。

## 三、P0：决定"查不查得出"

### P0-1 词条抽取只保留正文前 300 字纯文本

- 根因：`scripts/obsidian_bridge.py:536`、`:581`，`snippet = plain[:300].replace("\n", " ")`
- 影响：表格被压成一行、换行丢失、300 字之后的内容整段消失。设定集拿到的是残句，任何基于它的检查都在残句上做
- 改法：抽 structured 而非 snippet——frontmatter 全字段 + 首个二级标题下的列表项/表格行按行保留；字数上限改为配置项（默认 1200），保留行结构
- 工作量：2–3 人日（含回归）
- 验收：拿一条含 5 行表格的词条，`build_setting_from_vault` 后设定集里能还原 5 行、每行不粘连

### P0-2 设定集没有"时间切片"结构，字面比对把演变判成矛盾

- 根因：`scripts/utils/setting_schema.py:40-45` 条目字段只有 `name/tags/type/snippet`（无时代维度）；`scripts/utils/material_state.py:128-171` `detect_conflicts` 对同名字段的**非空字面差异**一律判 `review`
- 影响：两个方向都错
  - 假阳性：把"可见"与"隐藏"写进同一条目 → 判冲突，等作者拍板。写对了还挨红
  - 假阴性：拆成两个不同名条目 → 永不互相比对，正确与错误都看不见
- 改法：schema 增加可选 `phases: [{era, fields}]`；`detect_conflicts` 只在**同一 phase 内**比对同名同字段，无 phase 的条目退回现行规则（完全向后兼容）
- 工作量：3–4 人日
- 验收：同一夹具跑两次——同条目两 phase 各一个值 → 冲突 0；同 phase 内两个不同值 → 冲突 1

### P0-3 self 引擎下所有模型检查只出任务书，且没有任何提示

- 根因：`config/system.yaml` 的 `engine: self` + `NEEDS_MODEL_ENDPOINTS` 前置 400（设计如此，不是 bug）
- 影响：阶段 5"done"看起来像查过了，实际只生成了一份任务书；作者对"体检通过"的印象是假的
- 改法：不改设计，只改可见性——阶段完成回报与状态页固定显示"本阶段实际执行方式：self（未做模型检查）"；`nfctl status` 同字段
- 工作量：0.5 人日
- 验收：self 工作区跑完 stage5，progress/界面出现该标记；direct 下不出现

### P0-4 canon 未冻结时，冲突清单永远返回空

- 根因：`canon.json` 由 `approve.py --stage 1` 冻结；未冻结时 `/setting/canon` 返回 `exists:false`，`/setting/conflicts` 返回 `checked:false` + 空清单
- 影响：接口语义是对的（已刻意透出 `checked=false`），但**读的人会把空清单读成"没问题"**——这正是素材状态机 W7 的旧教训
- 改法：界面加红条"设定集未冻结，冲突检查未启用"；`nfctl status` 加一行 canon 状态
- 工作量：0.5 人日

## 四、P1：决定"查得全不全"

### P1-1 原作正文不在输入面

管线只吃 `materials/raw` 与知识库词条，原作正文库整体缺席。结果是"设定集里没写的事实 = 不存在"。

- 改法：新增只读输入 `materials/source/`（存引用清单不复制原文）+ 一个 importer：给定目录与关键词，产出三列清单（出处 / 作品内部时间 / 原文摘录）作为素材卡，交给 stage1 归并
- 内部时间是关键：没有它，两处描写是"同一时期互斥"还是"不同时期正常演变"根本判不了
- 工作量：2 人日
- 验收：对该目录扫一次，输出可复算的命中表；同一关键词重跑结果一致

### P1-2 阶段 5 分批 ≤5 章，跨批不共享上下文

- 根因：`scripts/stage5_check.py:226-233`，批大小由 max_tokens 反推，批间无共享
- 影响：跨批的时序/设定一致性问题结构上看不见；一条设定在第 2 章出现、第 12 章矛盾，永远不报
- 改法：批间注入账本摘要（`utils/memory_policy.py` 已有把 `story_state` 注入写作上下文的先例，复用它）；或阶段末补一遍"全书时间线复核"（只读章首段 + 账本）
- 工作量：2 人日
- 验收：夹具第 2 章与第 12 章各一处冲突，旧版 0 命中，新版 1 命中

### P1-3 阶段 5 提示词没有"时代特征"检查项

- 根因：`prompts/stage5_check.md:18-25` 七项检查（连贯/时序/空间/指代/关系/人设/常识），无"器物与制度是否符合该场景所处年代"
- 改法：加第 8 项。**提示词属作者权限，需你改**，agent 不代改
- 工作量：0.5 人日

### P1-4 一致性账本从未生成

`data/state/story_state.json` 不存在。它承载死亡 / 物品去向 / 年份逆序三类确定性判据（`scripts/utils/story_state.py`），零 token。没生成 = 判据空转。

- 改法：阶段 4、阶段 5 结束时强制跑一次；`nfctl status` 显示"账本：N 事件 / M 冲突"
- 工作量：0.5 人日
- 验收：10 章正文跑完，账本事件数 > 0；人为制造一次"死而复生"能被 `check()` 判出

### P1-5 设定改了，旧章不复检

阶段 5 见 `checked/` 已存在且有效即跳过（`stage5_check.py` 跳过分支）。设定集改动后，前面已过检的章不会重查。

- 改法：把 `setting.json` 内容指纹写进 progress；指纹变化时把已 checked 章标 `stale`，列出受影响章等作者决定，不自动重跑
- 工作量：2–3 人日
- 验收：改一次设定集，旧章列表出现 stale 标记；不改则无

## 五、P2：结构性，别急着动

- **状态追踪缺位**：`appearances.py` 只统计出场章与次数；`story_state.py` 只判死亡/物品/年份。角色"知道什么、在哪、身上有什么"没有账本
- **伏笔只从大纲取**：`utils/foreshadow.py` 用章大纲的"悬念钩子"字段，正文里现埋的伏笔不入账
- **两套检查并存**：`chapter_review.py` 与 stage5 各带一份设定集路径与判据，长期必然漂移
- **"函数在、判据空"是本病**：`utils/story_state.py` 开头自述，`quality_checklist.check_consistency()` 曾只判"本章有没有提到任一角色名"。建议立一条规矩：**新增检查器必须同时交一个"能判红"的最小用例**，否则不算完成

## 六、不建议做的

- 给模型挂"通读全书找矛盾"的常驻任务：token 不可控、结果不可回归、每次都换说法
- 在检查层做中文 NER / 关系抽取：误报率会让人开始无视红灯，比不报更糟
- 为"设定演变"上图数据库或事件溯源框架：当前规模用数组 + 指纹足够，引入后无人维护

## 七、建议落地顺序

```
P0-3 → P0-4   （半天，先把"没查"这件事说出来）
P0-1          （把数据补完整）
P0-2          （把误报去掉）
P1-4 → P1-5   （让账本与复检闭环）
P1-1 → P1-2 → P1-3
```

总估：P0 约 5–6 人日，P1 约 7 人日，P2 待定。

统一验收夹具：一条同名条目带两个时代切片 + 一章故意写错时代特征。改前跑，全绿（说明漏）；改后跑，只命中那一处。
