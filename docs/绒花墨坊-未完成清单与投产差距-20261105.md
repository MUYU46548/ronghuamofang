## 〇、一句话

**书已经能一本本产出来了，卡点不在“能不能写”，在“产出来的东西有没有被验收、能不能装进包里交出去”。**

## 一、“可以投入使用”的定义（按你自己的契约）

`立项契约.md` REV-002 把出口定为 **“能用级成品 word”**：作者验收后直接进入逐字修改工序。
产品基线把可用性判定从“AI 写得好不好”挪到了 **BROE（单点干预半径）**：
你改一处，系统被迫连带重做的最小单位是段、章还是全书。当前基线 = **整章**，目标 = **段**。

所以“投产”不是“功能齐了”，而是这四句能同时成立：

1. 一本真书（你的素材、你的题材）从零跑到 Word，**没有人手工补环节**；
2. 每章过得了字数与结构闸门，**导出的就是最新稿**；
3. 你改任意一段，**不触发整章重写**，改完能核对；
4. 装到别人机器上（或重装后）**行为一致**，不需要你在命令行救场。

- 判定记录：3 章回测，`ok 0 / 未定 3 / 缺陷 530`；`evidence.capability.verified = false`（没有基准集，能力证据为空）。

### 3.3 接管半径仍是章级
- 产品基线 §零：一期只能证明“系统没有多做”，证明不了“系统能少做”；且**每跑一轮流水线，标过的段全部失效**（P4 已接受，但必须显式告知）。
- 段落精修工作台能做“定点重写”，但它不改变流水线的重算单位；BROE=段 仍是目标不是现状。

## 六、距离投产：三段的现实工期

### 段 1 · 把“能装、能跑完一本”做实（预计 1–2 天）

1. `nfctl release-check` 红项清零 → 版本号升 0.8.2 → `npm run dist` 出包；
2. 安装包上跑一本 12 章（**外部 Agent 主路径**，与你现在用法一致），再补跑一次 `direct` 仅作对照；
3. 记录：每章汉字数、阶段耗时、Agent token 花费、失败与重试次数；
4. 发 GitHub Release（打包 + 说明 + 迁移指引）。

**出口判据**：12 章全部 ≥5000 汉字（或明确走“接受不达标 + 导出清单确认”）；Word 能开、章标题/目录/页边距对；安装版外部 Agent 接得上。

### 段 2 · 把“作者能接住”做实（预计 3–5 天）

1. 真书素材（你的库）→ 设定集 → 大纲 → 12 章；
2. 跑判定，**你逐章勾“几件事”**，至少走通一次“需定点重写 → 改 → 复判 → 合格”；
3. 用段落精修工作台改 3–5 段，记录：是否触发整章重算、改一处要等多久（BROE 实测值）；
4. 导出 Word，逐章核对“导出的就是最新的”。

**出口判据**：一本真书你愿意署名；至少 1 章从“不合格”走到“合格”全程留痕。

### 段 3 · 把“日常敢用”做实（预计 1–2 周）

词表 GUI → UI 统一 → 多库 → Best-of-N → 批注漂移；同时把 C 档工程欠账（尤其字数口径）清掉。
