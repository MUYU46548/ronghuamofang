# 重跑单章（第 N 章）影响面盘点（2026-11-04）

> 对应 `task-20261104-002` 第一步：**先盘点，再改语义**。
> 盘点方法：读实现（`nf_api.act_rewrite_chapter` / `_prepare_chapter_rewrite` /
> `stage4_writing.run_stage` / `stage5_check.run_stage` / `stage6_polish.run_stage` /
> `reject.py`），按"谁在什么时机写它"列表；不靠运行一遍看现象（那要烧 token）。

## 0. 先分清三条"重跑"入口（用户说的"重跑"可能是其中任意一条）

| 入口 | 后端 | 范围 | 现状 |
|---|---|---|---|
| 章节行「重写」 | `POST /chapters/rewrite {n}` → `act_rewrite_chapter` | **只重写 raw/NN.md** | 三层不同步：检查稿/润色稿/评审/判定全是旧的 |
| 「从阶段 N 重跑」 | `reject.py --stage N` → 清**整本**该阶段及下游产物 | 全书 | 语义正确（阶段级打回），但用户会误当成"重跑某一章" |
| `POST /stage/{n}/run {chapters:[N]}` | orchestrator `chapters` 参数 | 只有**阶段 4** 认这个范围 | 阶段 5/6 收到范围也不生效（`_extra` 只给 n==4） |

结论：真正缺的是**单章纵向重跑**（4→5→6 只做这一章），不是再改一遍 `reject.py`。

## 2. 阶段级打回（reject.py）**不改**

`reject.py` 的"清整本该阶段及下游"是审批打回的正当语义（用户按的是"这个阶段我不满意"），
不能为了单章把它改成合并 —— 那会让"打回重来"变成"半新半旧"。

要补的是**另一个动作**：`POST /chapters/rerun {n, through}`，
范围 = 第 N 章的 raw → checked → refined，其他章一个字节不动。

## 3. 单章重跑的判据（哈希 + mtime，不靠"看起来没变"）

重跑第 3 章（`through=6`）之后，必须逐项成立：

- 第 1/2/4 章的 `raw|checked|refined/NN.md`：**sha256 与 mtime 都不变**；
- `progress.json`：`stages.1/2/3/7/8` 与 `stages.5/6` 的 `approved` 不变；
  `stages.4.completed_chapters` 仍含全部已写章；其他章的 `invalid/needs_rewrite` 不变；
- 第 3 章：`raw` 是新内容（sha 变），`checked/refined` 存在且可用，`checked_pending/03.md` 不存在；
- `rolling.md`：只有 `### 第3章` 段变化，其他章段与 `global_summary` 不变；
- `appearances.json`：除 `generated_at` 外，只有第 3 章相关计数可能变；
- `data/review/`：只有 `03.json` 变（范围含 5 时）。

## 4. 改动面（按依赖顺序）

1. `stage5_check.run_stage(..., chapters=None)` / `stage6_polish.run_stage(..., chapters=None)`
   —— 范围只缩"这一轮处理哪些章"，断点/可用性判据一条不改；
2. `orchestrator.run` 的 `_extra`：范围对 4/5/6 都生效（现在只给 4）；
3. 新模块 `utils/chapter_rerun.py`：快照 → 备份下游 → 清本章标记 → 收尾（不改别的章）；
4. `nf_api.act_rerun_chapter` + `POST /chapters/rerun`；
5. GUI：章节行「重写」旁加"范围"（只重写正文 / 正文+检查+润色），文案明说影响面；
6. 用例：临时项目根造 4 章 + 假客户端，跑 `through=6`，断言上面第 3 节的哈希与 mtime。

## 5. 明确不做的

- 不把 `reject.py` 改成按章清（打回就是打回）；
- 不在单章重跑时清 `data/merged/`、`output/`（那是阶段 7/8 的产物，界面提示重跑）；
- 不自动重跑 `judge` 全书回测后在界面上"悄悄改结论" —— 重跑后由作者点"重跑判定"或由本动作显式带上 `refresh_judge`。

### 6.2 跑起来才暴露的三处真缺陷（都已修）

1. **stage4 完成却停在 `running`**：`chapters` 分支里 `_partial_or_done` 返回 True 时提前 `return`，
   而那个分支只写 partial 不写 done —— 正文写完了、界面像卡死。修法：True 落到 `set_stage(4,"done")`。
2. **YAML 1.1 把 `off` 解析成布尔 False**：`str(False).lower() != "off"` → 裁定闸“关不掉”，
   `checked_pending/` 被写满。修法：`utils/config_io.as_flag()` 统一认 `off/on/yes/no`，
   `gates.stage5_diff` 与 `gates.setting_coherence` 两处同族判据一起改。
3. **FakeClient 无视批范围**：stage5 把 `raw/` 全量复制到 `checked/`、stage6 复制全量 `checked→refined`，
   单章重跑时范围外章节被覆盖（内容与 mtime 双变），下游据此判“上游改过”把全书重算一遍。
   修法：task 文本/任务名里的批范围优先，认不出才退回全量。

### 6.4 遗留（如实记）

- **`nf_api` 的 `--root` 与 cwd 不一致时单章重跑会写错项目**：`orchestrator.run` 内部仍是 cwd 相对路径
  （`RunLock("data/state/run.lock")` 等），生产由 Electron `spawn(..., {cwd: ws})` 与 `--root ws` 同时传，
  两者恒等所以没暴露；用一个临时根、但 cwd 留在仓库时跑，阶段产物会落在 cwd。
  本轮真后端验收因此按**生产同构**（cwd=项目根）执行。收口办法是让 orchestrator 全走 `NF_ROOT`/绝对路径 ——
  改动面横跨 4 个阶段脚本，单独立卡，不塞进本批。
