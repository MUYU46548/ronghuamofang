## 一、讨论（DiscussionQueue / DiscussThreadPanel）

**是什么**：按“第 N 章 + 一个主题”开一条讨论，你发言、AI 发言。AI 的每一句要带证据
（引用正文必须真的命中原文；设定/判定/大纲类也要指出出处），说完能落成动作：
`建议修改` / `整章重写` / `改某一段`（最后这个与读改链是同一个出口）。**拍板只有你能做**
——`decide` 不对 Agent 开放，DSH/Hermes 只能开题、读、发言。

**怎么用**：审阅台里的讨论面板；MCP 面给了 4 个工具（`nf_discuss_list/read/open/say`）。

**花多少**：一轮 AI 发言 = 1 次调用；输入 = 本章正文 + 本章大纲 + 最近几轮 + 压缩摘要
（一章 6k–10k token 量级），输出上限 **1600 token**。一次讨论 10 轮 ≈ 10 次调用。

**维护面**：`discuss_thread.py` 513 行 + `utils/discuss_ai.py` 585 行 + 两个面板约 970 行；
8 个用例文件约 225 条 check；**2026-11-16 还在加功能**（“讨论说完能变成动作”）。

**与读改的关系**：它是“想”的入口，读改是“做”的入口；动作出口已经并到段落精修，
等于共用同一把刀。它不是逐段审阅，也不产生 diff。

**三个选项**：
- A 继续投入：把它当读改的上游（例如“讨论结论一键生成批注/候选”）。与“不再加新功能”的定案冲突。
- **B 冻结（建议）**：能说、能记、能落现有三种动作，不再加动作种类。数据在 `data/discuss/`。
- C 停更入口：隐藏页签；数据不动，命令行/Agent 面仍可用。

**建议理由**：动作种类已经覆盖“提意见 → 改一段/整章”；再扩就是把聊天界面做成编辑器，
与你“读改在墨坊、聊天交给宿主”的方向相反。

## 二、多写几版（Best-of-N）

**是什么**：同一章、同一条修订意见跑 N 次，产出 N 版；用五维确定性打分排序
（字数 / 病灶词 / 段落 / 复读 / 与目标贴合），胜者写回正文，**所有候选都留证**
（`data/state/candidates/chNN/` + `result.json` 含每版分数与理由）。

**怎么用**：章节页“多写几版再挑”开关（默认 **0 关**）；真正触发点在自动重写（低分章 + 审查报告）。

**花多少**：**N 倍整章重写**。一版输出 4k–7k 汉字；N=3 就是三次整章调用。这是全项目里
单价最高的动作之一，所以默认关、且必须作者按章开。

**维护面**：`utils/best_of_n.py` 263 行 + CLI 23 行 + 候选面板 209 行；21 条用例；
**2026-11-07 之后没再改动**。

**与读改的关系**：整章级、属于“跑”；逐段读改已经有“一次调用出 3 条候选、切换不花钱”，
覆盖了“多版本比较”的需求，且便宜得多。

**三个选项**：
- A 继续投入：把打分接进判定引擎、做“按段落版”。成本高、判据弱，不建议。
- B 冻结保留：开关留着，默认关。
- **C 停更入口（建议）**：隐藏“多写几版”开关；`best_of_n.py` 与 CLI 保留，需要时仍可跑。

**建议理由**：你已不跑书；它唯一的自动触发点在自动重写里，等于一条不会走的路。
代码留着不碍事，但界面上摆一个“点了就花 N 倍钱”的开关，是把风险留在手边。

## 三、沙盒（SandboxQueue）

**是什么**：把“要写进设定库”的候选草稿排队；通过 / 驳回 / 退回**只改审核状态**，
不动沙盒里的文件，**永不写 Obsidian**。粘贴进知识库始终由你手工完成。

**怎么用**：审核页签（带待审数徽标）；MCP 面 2 个工具（看队列、驳回）。

**花多少**：0（不调模型）。

**维护面**：`sandbox.py` 域模块 + `SandboxQueue.vue` 318 行；88 条用例（含 advisor）。

**与读改的关系**：不同族（它管设定库，不管正文）。但它体现的原则与读改一致：
**候选摊开、作者拍板、系统不替你入库**。

**三个选项**：
- A 继续投入：接 ROSA 词条生成（但生成端已冻结，没有新生成器）。
- **B 只读保留（建议）**：队列与状态可查可标；不再扩。
- C 停用入口：隐藏审核页签（待审数徽标会一起消失）。

**建议理由**：零成本、零风险，且它是“系统绝不越权写 vault”这条红线的可见证据。
唯一要注意的是：保持现状意味着它只在“已有候选”时有用。

## 四、成书提炼（book_extract）

**是什么**：把一本写完的书（旧稿 / 前作 / 参照作品）拆章 → 逐章摘要 → 角色卡 / 设定卡 /
时间线 / 伏笔 / 冲突 / 病灶词 → **只增不改**地并进 `setting.json`（写前备份）。

**怎么用**：CLI 五条命令（`init / run --dry-run / run / status / merge`）；
章节页签有折叠块 GUI（预演 → 后台跑 → 合并预览 → 确认）。

**花多少**：预演给公式 —— 摘要 **n 次** + 角色/时间线/设定 **3 × 批数**（每 30 章一批）+
伏笔 **1 次** + 一致性 **n/3 次**。40 章 ≈ **57 次调用**；摘要输入一章 6k–10k token。
要求 `engine: direct`（子会话接不了整段请求）。

**维护面**：`utils/book_extract/` 约 2.5k 行 + CLI/域模块约 470 行 + GUI 在 `App.vue`；
34 条用例 + 1 套 e2e；断点续跑（一章失败不重烧整本）。

**与读改的关系**：不同族，但产出的角色/设定/时间线**正是读改时判断“这段合不合设定”的原料**。
它也是“跨项目复用旧稿”的唯一入口。

**三个选项**：
- A 继续投入：分卷、续作、多书合并。
- **B 保留 CLI、冻结 GUI（建议）**：低频动作，命令行足够；界面那块不再改。
- C 停更入口：连 CLI 说明也收起（不推荐，成本几乎为零的东西没必要藏）。

**建议理由**：一年用几次、单次成本可控、产物直接喂读改；但界面维护是纯负担。
它不在 Agent 白名单里（`nf_mcp` 没暴露），也就不用担心外部 Agent 偷偷烧钱。
