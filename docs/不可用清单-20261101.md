# 绒花墨坊 · 不可用清单（按使用顺序）

> 方法：**从使用者的座位走一遍，不从代码走。** 每一步只问三件事：我能做什么／我停得下来吗／我停了能改吗。
> 判据：**"界面上有，但按了没用或用了更糟"也算断点** —— 那比没有更糟，因为它骗你以为能控制。
> 本文不含版本号、不含分期、不含排期。只有断点 + 最小改法 + 会失败的反证。
> 依据：真实使用数据（`%APPDATA%\绒花墨坊\workspace`，47 次运行、393 个章节文件、一份成品 Word）+ 代码位置。

---

## 结论

**不可用。** 不是因为功能少，是因为**从按下开始到拿到稿子，没有任何一个点是人能作主的**。
唯一真正生效的控制是"停止"，而停止的定价是一整章。

下面 10 条，按你实际会走的顺序排。

## 1 · 开始跑：没法定"跑到哪为止"

| | |
|---|---|
| 你能做什么 | 选阶段（跑 4），或者全自动跑 |
| 卡在哪 | **只有阶段粒度，没有章粒度。** 阶段 4 一旦开始，会把所有未完成章一口气写完 |
| 位置 | `stage4_writing.py` 的 argparse 只有 `--task-dir`，无章节范围参数；`orchestrator.py` 按阶段 for 循环 |
| 最小改法 | 给阶段 4 加 `--chapters 1-3` / `--max-chapters N`，GUI 上变成「先写 3 章看看」 |
| 反证 | 指定 `--chapters 3` 后若实际写了 4 章 → 红 |

**为什么这是第一条**：不能限定范围，后面所有"停下来看看"都无从谈起——因为它根本不给你停的机会，它是整本跑完才停。

---

## 2 · 跑起来：暂停是假的

| | |
|---|---|
| 你能做什么 | 点「暂停」 |
| 卡在哪 | **暂停的是屏幕上的字，不是模型的笔。** `/stream/pause` 只是把一个 Event 置位，该 Event 只在 SSE 推送函数里被检查（`_push`），模型调用照跑照计费 |
| 更糟的 | 界面提示是「**已暂停输出，可修改提示词后点恢复**」—— 本次调用的 prompt 早已发出，改了对这一次**完全无效** |
| 位置 | `nf_api.py:2878-2896`（只 set Event）、`nf_api.py:436-452`（Event 只在 `_push` 里查）、`App.vue:1456-1463`（提示语） |
| 最小改法 | ① 提示语改成真话：「已暂停**显示**，模型仍在生成、仍在计费」；② 或让它真暂停：pause 时同时置 `stop_flag`，resume 时从断点续（成本高，先做①） |
| 反证 | 暂停 60 秒后 `cost_log` 仍新增 token → 证明"暂停"没停计费；若提示语仍写"可修改提示词" → 红 |

## 3 · 想停：停一次亏一整章

| | |
|---|---|
| 你能做什么 | 点「停止」 |
| 卡在哪 | **当前章半截直接丢弃，不入稿。** 已完成的章保住，正在写的那一章全丢 |
| 位置 | `stage4_writing.py:1506-1511`：`"当前章半截不入稿"` |
| 最小改法 | 停止时把已收到的文本落到 `data/state/truncated/NN.md`，章状态标 `partial`，界面给「接着写」/「采纳为草稿」/「丢弃」三个选项（残稿机制已存在，只是没接在"用户停止"这条路径上） |
| 反证 | 写第 2 章中途停止后，`truncated/02.md` 不存在或为空 → 红 |

**这条解释了"只能丢进去一直跑"**：停一次亏一章几千字，理性选择就是不停。

## 4 · 想改方向：没有入口

| | |
|---|---|
| 你能做什么 | 什么都不能做 |

| 位置 | `/intervene` 全项目 **0 命中** |

| 反证 | 干预后第 N+1 章的任务里找不到该指令原文 → 红；干预影响了第 N 章 → 红 |

## 5 · 跑完了：2000 字的章被判合格

| | |
|---|---|
| 你能做什么 | 看结论：整本「完成」 |
| 卡在哪 | **10 章全部低于 5000 下限，全部判 ok。** 自评分 8–9 分 |
| 实测 | 润色稿字数：`2163 2438 2474 2796 2257 1968 2692 2697 2338 2452`（全书 2.4 万字）；`chapter_log` 记 `status=ok, quality=8~9` |
| 位置 | `prompts/stage4_writing.md` 自评分注释 + `stage4_writing.py:1132` 按 `quality>=threshold` 判状态 |
| 最小改法 | 字数不达标 → **状态不许写 ok**（字数是确定性判据，不该由模型自评决定）；自评分降为参考信息，不参与状态 |

## 6 · 想让章变长：代价失控

| | |
|---|---|
| 你能做什么 | 重跑这一章 |
| 卡在哪 | **单章烧 200 万 token、跑 40–90 分钟、然后失败。** 同样任务，直连引擎只要 6.5 万 |
| 实测 | `run 45`：4 小时 40 分 / **输入 791 万** / interrupted；`run 46`：67 分 / **603 万** / failed；`run 47`：**218 万** / failed。对照 `run 40`（直连）：10 章共 65 万、30 分钟 |
| 位置 | `cost_log` 按 run 分组的输入合计（`%APPDATA%\绒花墨坊\workspace\logs\runs.db`） |
| 用哪个引擎是你的决定 | 这里只陈述一个事实：**补长一章，两种引擎差 30 倍，且高价那条会失败** |
| 最小改法 | 不是改代码，是**先让"补长"这件事有上限**：单章重试设次数与 token 上限，超了就停并报「这一章补不上去，原因 X」，而不是烧到熔断 |
| 反证 | 重试 3 次后仍无上限、继续烧 → 红 |

## 7 · 终于长出来了：下游压回去

| | |
|---|---|
| 你能做什么 | 看三稿对照（只读） |

| 反证 | 造一章 7000 字走全链，缩到 2500 而界面无任何提示 → 红 |

## 10 · 两个 agent 同时用：必炸

| | |
|---|---|
| 你能做什么 | 不知道有第二个在用 |
| 卡在哪 | **锁只装在总闸上。** `RunLock` 全项目只有 `orchestrator.py:311` 一处调用；段落重写、保存正文、改设定、审批、打回、plan 落盘**全部裸写** |
| 更糟的 | `CURRENT["id"]` 是**进程内**变量，只拦"起第二条流水线"，不拦"流水线跑着时有人改章" |
| 位置 | `utils/run_lock.py`（有）、`orchestrator.py:311`（唯一使用者）、`nf_api.py:1141`（只拦起 job） |
| 最小改法 | ① 所有写端点进入前检查 `run.lock` 是否被**别的活进程**持有，是则 409；② `nf_api` 启动时若锁已被活进程持有 → 拒绝启动并说明是谁 |
| 反证 | 手工占住 `run.lock` 后调用 `/chapters/save` 仍返回 200 → 红 |

## 这 10 条的性质不一样，别混着做

| 类 | 条 | 性质 |
|---|---|---|
| **假控制**（有按钮但没用/更糟） | 2、9 | 改提示语 + 一个标记，**各半天**，但先改这个——它们正在骗你 |
| **惩罚式控制**（有按钮但代价太高） | 3、4、1 | 残稿落地 + 干预通道 + 章范围，**2–3 天**，这是"能拉住"的全部 |
| **判据放行** | 5 | 让确定性判据接管状态，**1 天** |
| **生成侧**（不是交互问题） | 6、7 | 重试上限 + 缩减告警，**各半天**；真正的产能问题不在这里解决 |
| **数据安全** | 10 | 写锁 + 单实例，**1 天**，越早越好 |

**如果只做一件**：第 10 条。它不改善体验，但它是唯一会**毁掉你已有东西**的那条。

**如果只做能改善体验的一件**：第 3 条。残稿落地之后，"停一下"才不再是惩罚，人才敢拦——这是"拉不住"的正面解法。
