## [业务界定卡]

### 1. 服务对象

**一个人。** 他同时是唯一作者和唯一开发者，永不用终端，只有 GUI。〔基线一·使用者〕

业务上他不是"网文作者群体"，不能按人群做画像；只有一个样本，且样本的另一半身份（开发者）会污染他的判断——他比任何用户都更清楚系统内部有什么，却依然说"什么都点不了"〔原话 1/2〕。这说明问题不在"他不知道怎么用"，在"入口不存在"。

#### 他的时间里，这个工具占哪一段

一天分三段：**构思段**（想清楚要写什么）、**产出段**（把字数落到纸上）、**收束段**（把稿子弄成能交的样子）。

- 这个工具只占 **产出段**，不占构思段——因为定位是"代写""让我写得更快"〔原话 6〕，价值主张是"人写撑死一天两万字，AI 一两天给你几十万字"〔原话 8〕。
- 工具**必须能在无人看管的状态下占住整段产出时间**。他明确说"只能丢在 agent 里一直跑，一点交互一点控制力都没有，完全拉不住"〔原话 4〕——"丢在里一直跑"是他被迫采用的方式，不是他想要的交互，但它反证了一件事：**"守着它跑"对他不是资产，是负债。**
- 因此接管的时点只能在 **AI 停手之后**，不能在生成之中（"边写边介入"已被否〔基线五·4〕）。这不是偏好，是他的时间预算决定的。

#### 他不能做什么（业务约束，不是能力缺陷）

| 不能 | 依据 |
|---|---|
| 不能在等待中保持在场（4 小时 40 分的一次重跑） | §2.4 run45 |
| 不能说清楚"我想要的到底是什么"——所以需要"我自己改"，而不是"再许愿一次" | 断点 8 |
| 不能承担"改一处 = 整章重来"的代价 | 断点 3 / 6 |
| 不能同时维持四个写入入口的心智（GUI / HTTP / MCP / CLI） | 基线一·写入入口、断点 10 |
| 不能用终端、不看日志、不读代码 | 基线一·使用者 |

### 2. 业务问题（一句话）

**AI 能把字写出来，但作者接不住；接不住的那部分既不能就地改，也不能只改那一处，只能整章重来——而重来比一开始自己写还贵。**

### 3. “不可用”的业务定义

> 不是"AI 写得差"。他本人已经把"AI 写得差"设成了常量：**"全世界 AI 写的我都读不下去"**，且认为本产品"已经把垃圾的质量提升几千倍"〔原话 7〕，同时给出天花板"真人一半水平都算了不起"〔原话 6〕。
> 质量既然恒为负、且他自愿接受，**质量就不能进"可用性"的判定式**。

**业务定义：**
设 `T_接管` = 作者把 AI 初稿变成"自己愿意署名的稿子"所必须亲手投入的时间；`T_自写` = 他从零写同一章所需时间。

- `T_接管 < T_自写` → **可用**。（哪怕 AI 只到一半水平，只要接管比自写省，他就用。）
- `T_接管 ≥ T_自写` → **不可用**。（AI 写得再好，只要改不动，他还是自己写更快。）
- **接管路径不存在时 `T_接管 = ∞`** → **"根本不可用"**。这正是原话 5 的判定，也是它和原话 6 不矛盾的原因：他接受低质量，但不接受"没有接管路径"。

由此推出三个**并行必要条件**，任一不满足即判不可用：

| 条件 | 业务含义 | 当前是否成立 | 依据 |
|---|---|---|---|
| C1 接管可发生 | 存在针对"某一处"的入口，而不是针对"整章" | **否**（只有"提交 job 等 diff"） | 断点 8 |
| C2 接管是局部的 | 改一处不强制重做整章 | **否**（整章重生成；成品过期时退化为全书） | 断点 3/6/9 |
| C3 产物可信 | 作者看到的就是最终会印出来的；变了要告诉他 | **否**（成品 docx 无 stale；下压不告知） | 断点 7/9 |

补充一条**信任级**失效：`chapter_log` 在 10/10 章不达标时全线记 `ok`、`quality=8~9`〔§2.2〕。这使系统给出的任何"合格"结论都不可采信——作者被迫对全部产物重新人工验证，`T_接管` 因此被整体抬高。**判定不可信 = 接管成本翻倍**，这是业务问题，不是数据问题。

### 4. 业务价值与衡量

#### 唯一有效的主指标

**单点干预半径（BROE, Blast Radius of One Edit）**：作者改动一处文字时，系统被迫连带重做的最小单位——`段 / 章 / 全书`。

选它的理由（三条，逐条对上硬约束）：

1. **与"AI 写得好不好"完全正交。** 它计量的是系统的重做范围，不是文本的好坏。AI 写得再烂，只要半径是"段"，作者就敢一段一段改到能署名；AI 写得再好，只要半径是"章"，他改一个字就得重赌一次，仍然"不敢动"。
2. **可复验、不需要作者主观判断。** 看 `runs.db` 有没有新增 run、看未改动段落的 diff 是否为空、看产物是否被整体重出。判据不会因为"他读不下去"而永不亮（这正是否掉方向 2 的原因）。
3. **直接对上他的原话。** "不可控不可改"〔原话 5〕在业务上就是"半径过大"；"拉不住"〔原话 4〕就是"没有落点"。

**当前基线：`整章`（最坏退化为 `全书`）。** 依据：停止即丢整章〔断点 3〕、改一处须提交 job 等 diff〔断点 8〕、补长须整章重跑且 3/3 未成功（run45 interrupted / run46 failed / run47 failed）〔§2.4〕、源改动后成品无标记〔断点 9〕。
**目标口径**：降至 `段`。**该目标值本身需实测确认是否可达**——本团不做技术承诺。

#### 辅助指标（只作护栏，不单独作为价值证明）

| 指标 | 业务含义 | 当前基线 | 溯源 |
|---|---|---|---|
| 干预入口覆盖率 | 作者"想改的每一处"，GUI 内是否有同屏入口 | 1 个，且非同屏（选段→填意见→提交 job→等→看 diff） | 断点 8 |
| 中止损失 | 叫停时已生成内容被丢弃的量 | 整章 | 断点 3 |
| 判定一致率 | 字数低于下限却判合格的比例 | 0%（10/10 章不达标判 ok/8~9） | §2.2 |
| 下压可见性 | 阶段间字数大幅下降是否被告知 | 无（7184→2474、7024→2257 静默） | §2.3 |
| 产物新鲜度可见性 | 源改动后成品是否被标记过期 | 无（docx 无 stale；`judge` 有 stale 但成品无） | 断点 9 |
| 单章成本放大率 | 补长一章 vs 从零直连写一章 | 218–288 万 token / 40 分钟–4 小时 40 分；直连 10 章 64.9 万 token / 30 分钟。**口径未对齐，比值需实测** | §2.4 |
| 并发写安全 | 两入口同时写是否损坏数据 | 未互斥，"必炸"（`RunLock` 仅一处调用） | 断点 10 |

> 注：`T_接管 / T_自写` 是他真正关心的比值，但会随文本质量浮动，故**不作主指标**，仅作为业务定义的判定式（§3）。主指标取其结构性代理量 BROE。

### 5. 产品边界

**做（本产品存在的理由）：**
- 让作者**能接管** AI 产出：能定位到一处、能就地改、改完不用重赌整章。
- 让作者**知道自己在哪**：跑到第几章、花了多少、哪一版是当前的、哪些已经过期。
- 让作者**停得下来**：停下来不损失、不白花钱。
- 让作者的**每一次动作互不踩踏**：单写者，四个入口同一套真相。

**不做：**
- 不做文本质量的提升（换模型、调提示词、加评分以求"读得下去"）——已被否〔基线五·1〕，且与 §3 的定义冲突。
- 不做多人协作、账号体系、云端同步（只有一个作者）。
- 不做发布分发、平台对接、版权检测、封面排版。
- 不做"生成过程中持续在场"的共写形态——与"就是快"直接冲突〔基线五·4〕。
- 不做引擎选型（hermes vs 直连）。这是产品负责人的决定，本团不出建议〔§2.4 原注〕。

**本阶段（一期）明确不做：**
1. **不重写八阶段流水线结构**。八阶段是既成事实，一期只在其上打通"接管"，不动阶段划分。
2. **不新建第九阶段**（不做"人工精修阶段""审校阶段"之类）。
3. **不做质量评分体系**，反而要**收缩**现有评分在状态判定中的权重〔断点 5〕——一期只保证"硬指标不撒谎"，不保证"软评分准"。
4. **不做历史数据追溯修复**：47 次 run、393 个章节文件的存量不做批量回填，只保证新产生的数据可信。
5. **不做数据层/存储重构**——除非为支撑"局部重算"必须的最小改动，且需研发确认（"界面好办、贵在数据层"这个顺序已被否〔基线五·5〕，一期不以此为起点）。
6. **不追求"跑一遍就好看"**。一期结束时产物仍然"读不下去"是**允许的**；不允许的是"读不下去时无处下手"。

## [场景清单]

角色只有一个作者，但按他在某一刻的身份分四类，因为验收主体不同：
- **A 下单人**——决定这一轮做多少（S01）
- **B 监工人**——运行中要知道发生了什么（S02–S05）
- **C 接管人**——把 AI 初稿改成自己要的样子（S06–S10）
- **D 署名人**——确认这版是我的、并拿到它（S11–S15）

**判据一律为二值/可数；无基线的一律标`需实测`；每条附"反证"——即该判据在什么情况下必须变红。**

| 编号 | 角色 | 场景 | 作者要完成的任务 | 完成判据（可判定） | 反证（判失败的条件） | 溯源 |
|---|---|---|---|---|---|---|
| **S01** | A | 开工前，决定"这一轮做到哪" | 指定本轮的章节范围/章数，然后启动 | ① GUI 存在章数或章节区间输入；② 启动后新增的章节文件数 = 设定值（误差 0）；③ `runs.db` 该 run 的章节记录数 = 设定值 | 只能选阶段、一跑就跑到所有未完成章 → 失败 | 断点 1 |
| **S02** | B | 运行中，离开一段时间后回来 | 判断"现在在哪、还剩多少、是不是还在跑" | ① 界面显示的当前章序与 workspace 实际已落盘章节数任一次采样差值为 0；② 界面"运行中"状态与进程真实状态一致（进程已死/已停时不得仍显示运行中）；③ 已消耗 token 与时长可读 | 显示在跑但实际已停、或显示暂停但仍在计费 → 失败 | 断点 2、§2.4 |
| **S03** | B | 发现方向不对，要立刻收手 | 停止，并保住已经写出来的东西 | ① 停止后已完成章节文件全部保留且可在 GUI 打开；② 被中断的那一章以"未完成"状态显式存在，不得静默消失、不得计入成品；③ 停止后 30 秒内相关文件字节数不再增长 | 停止 = 当前章整章丢弃、半截不入稿 → 失败 | 断点 3 |
| **S04** | B | 暂时想插一件事 / 想省点钱 | 暂停，并相信"暂停"意味着不再花钱 | ① 暂停后 30 秒内 `cost_log` 无新增行且无新增产物；② 暂停态的提示语不得包含在暂停态无法执行的指令（如"修改提示词"） | 暂停只停显示、模型照跑照计费，提示语仍写"可修改提示词" → 失败 | 断点 2 |
| **S05** | B | 跑到一半发现"这个方向不对，但不值得整个重来" | 在不停下整个运行的前提下，提交一次方向修正 | ① 存在运行中提交修正的入口；② 修正提交后，至少一章后续产物的输入中可核验到该修正（日志字段或产物内容）；③ 全程不产生新的 run（`runs.db` 行数不变） | 无干预通道（`/intervene` 0 命中）→ 失败 | 断点 4 |
| **S06** | C | 拿到初稿，读到某一段"这句我必须自己写" | 把这一段改成自己要的样子，并保存 | ① 从"指到这一段"到"改动落盘"全程在同一个页面内完成；② 不提交异步 job、不等待、不产生新 run；③ 保存后立即可见，且刷新/重开不丢 | 必须"选段→填意见→提交 job→等→看 diff"；或只能整章重跑 → 失败 | 断点 8 |
| **S07** | C | 改完之后，确认没伤到别处 | 只让改的那一处变，其它地方不动 | ① 一次段落级改动，未改动段落逐字 diff 为空（改动字符数 = 0）；② 该次改动触发的重算量显著低于整章重写（**比值需实测**）；③ 不触发全书重出成品 | 改一段导致整章重排甚至全书重出 → 失败 | 断点 3/6/9 |
| **S08** | C | 需要判断"这章到底算不算完成" | 拿到一个不会骗他的完成判定 | ① 任一章字数低于配置下限时，其状态不得为 `ok`、其质量分不得单独作为合格依据；② 以《潮汐档案》同口径回放，10/10 章应被判不达标；③ 被判定"不达标"时，界面给出可执行的下一步（补长 / 修改 / 接受） | 仍出现"2000 字判 ok、quality 8~9" → 失败 | 断点 5、§2.2 |
| **S09** | C | 发现正文写长了，但润色后变短了 | 知道"我的 7000 字去哪了"，并能选择保留哪一版 | ① 任一阶段使某章字数下降超过阈值时，GUI 必须可见告知（阈值**需实测/待定**）；② 被压缩前的版本可回溯、可对比；③ 成品取哪一版由作者可辨 | 7184→2474、7024→2257 静默发生，过程无告警 → 失败 | 断点 7、§2.3 |
| **S10** | C | 某章太短，要补长 | 补长这一章，且不为此付出失控代价 | ① 单章补长的成本与"从零直连写一章"同一量级（**比值需实测**）；② 失败后可重试，且重试不重复消耗已完成部分；③ 补长不改变其它章 | 218–288 万 token、40 分钟–4 小时 40 分、3/3 未成功且无替代路径 → 失败 | 断点 6、§2.4 |
| **S11** | D | 改了源稿，准备出成品 | 确认"我现在导出的就是最新的" | ① 源章节/任一项设定改动后，成品被标记"过期"；② 该标记在"合并出 Word"与"导出"两个动作上均被拦截或需显式确认；③ 可追到具体哪一章/哪一项变了 | 成品 docx 无 stale 标记，改完悄悄过期 → 失败 | 断点 9 |
| **S12** | D | 一边让外部 Agent 跑，一边自己在 GUI 里改 | 两件事同时做而不炸 | ① GUI 与外部 Agent 同时发起写操作时，后到者被明确拒绝并给出可读文案；② 任意并发写场景下文件损坏次数 = 0；③ 并发次数与损坏率**需实测**（压测口径待定） | 写操作裸写无锁、跨进程锁仅一处调用、"必炸" → 失败 | 断点 10 |
| **S13** | D | 外部 Agent 交了一批活，我要接手 | 在 GUI 里看见 agent 做了什么，并继续接管 | ① agent 入口产生的产物在 GUI 列表中可见；② 状态可辨（哪些是 agent 改的、改了什么）；③ 可在 GUI 内对该产物直接进入 S06 的接管路径 | 产物只在 agent 黑箱里、GUI 看不到或看不到改动 → 失败 | 原话 2、基线一·4 入口 |
| **S14** | D | 一轮跑完，要判断"钱花得值不值" | 看到这一轮的成本，并能止损 | ① 运行中与结束后均可读到本轮 token 与时长；② 触及预算上限时自动停止，而不是继续消耗；③ 账单可归到具体章节 | 预算配置存在但未按章归属、超限不停 → **需实测**（当前 `per_request_max_tokens` 比的是输出，hermes 输出约 3 万，不触发） | §2.5、§2.4 |
| **S15** | D | 稿子改到"我认了" | 确认这一版可用，并拿到与源一致的成品 | ① 导出件内容与当前源章节逐章一致（差异 0）；② 该成品带时间/版本可追；③ 作者做出"确认可用"动作后，该状态不得被后续流程静默推翻（要推翻必须告知） | 导出的不是当前源；或改完悄悄过期导致"认过的稿子"其实已变 → 失败 | 断点 9 |

## 附：本卡未覆盖、需下一阶段（产品定义）回答的问题

1. **BROE 从"章"降到"段"在什么条件下才算真的成立**——判据里"重算量显著低于"缺一个可测阈值，需实测后回填。
2. **S02 的"真实状态"如何被作者验证**——他没用终端，所以"进程已死"必须由 GUI 自己说出口，这条的判定方式需产品定义给出。
3. **S08 判"不达标"之后的三条出路（补长/修改/接受）哪一条是一期必须的**——本文只列场景，不排优先级。
4. **S12 的并发口径**：四个写入入口是否全部纳入同一把锁，属于产品定义范围，本文只要求"0 损坏"。
