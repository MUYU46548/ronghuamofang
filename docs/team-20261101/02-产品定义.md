# 02 · 产品定义（产品架构师）

> 依据：`00-事实基线.md`（下称〔基线〕）、`01-业务界定.md`（下称〔界定〕）。本文每条结论后标溯源。
> 本文不写代码、不定技术框架、不定接口细节（凡涉实现处一律标「待研发确认」）、不排期、不写版本号。
> 无实测依据的量一律标 **需实测**，并给出测法；不承诺技术可达。

**上游已定、本文不改的三条前提：**

1. 业务问题：AI 能把字写出来，但作者接不住；接不住的部分只能整章重来，而重来比自写还贵。〔界定·2〕
2. 「不可用」= `T_接管 ≥ T_自写`（接管路径不存在时 = ∞）。**质量不进可用性判定。**〔界定·3〕
3. 唯一主指标：**单点干预半径 BROE**。当前 = 整章（最坏退化全书），目标口径 = 段；目标值本身需实测。〔界定·4〕

## 1. 能力架构

### 1.0 组织的原则

能力不是按"模块"切的（模块切出来必然变成四个并列的菜单），而是按 **作者在接管链上依次会撞上的问题** 切的。每层只回答一个问题，答不上来，下面那层的问题就没有意义。

六层是一条**价值串联链**，不是并列：

- 缺 L0 → 接管的对象本身不确定（不知道停在哪、跑到哪、哪个是真的）。
- 缺 L1 → C1 根本不能发生：没有"某一处"这个入口。
- 缺 L2 → 入口在，但要价仍是"再许愿一次"，`T_接管` 不降，等于没入口。
- 缺 L3 → 有入口、能改，但改一处仍要重做整章，BROE 停在"章"。
- 缺 L4 → 半径虽小，但作者不敢相信看到的稿子就是最终稿，被迫对全部产物重新人工核对，`T_接管` 反而回弹。
- 缺 L5 → 任意一次并发写入把前五层的成果**静默**作废，且作者不知道作废了。

**L4 是最反直觉的一层**：它不是锦上添花，它决定 L3 的收益能否兑现。半径缩到段，但如果"段"是不可信的段，作者仍然要通读全章确认——省下的重算成本被复核成本吃回去。〔界定·3 补充信任级失效〕

---

### L0 · 边界能力 ——「这一轮，它被允许动到哪，什么时候必须停？」

| 项 | 内容 |
|---|---|
| 回答的问题 | 我这一轮让它做多少？它现在到哪了？我叫停之后，已经写出来的还在不在？我按了暂停，它还花不花钱？ |
| 场景 | S01、S02、S03、S04、S05 |
| 缺了会怎样 | 接管对象不确定：不知道跑没跑完、不知道停没停、不知道哪一版是本次跑出来的。作者无法判断"现在该接哪一份稿"，接管动作失去对象。S03 的现状更直接——**叫停即丢整章**，等于把要接管的东西先烧掉一半。〔断点 1/2/3〕 |
| 与三条件的关系 | C1/C2/C3 的前提，不单独归属。 |
| 关键约束 | 这一层的所有状态必须是**可核验的真实状态**，不是界面自己的布尔值。任何"按了没用"的控件（假暂停）会把 L4 直接打穿——作者一旦发现第一个控件撒谎，后面所有判定都不再被采信。〔断点 2〕 |

### L1 · 定位能力 ——「我要改的，是哪一处？」

| 项 | 内容 |
|---|---|
| 回答的问题 | 我心里有一句要改的话，怎么在界面里把它指出来？指出来之后，我能不能同时看到它在整章里的位置？ |
| 场景 | S06（"读到某一段，这句我必须自己写"）、S13 |
| 缺了会怎样 | **C1 不成立**。只有"章"这个粒度时，"某一处"在产品里没有指称对象，任何"改这里"的意图只能被翻译成"重写这一章"。这正是用户说"什么都点不了"的具体形态——不是按钮不够，是**没有被指的那个东西**。〔原话 1/2、断点 8〕 |
| 与三条件的关系 | **C1 的成立条件。** |

### L2 · 就地能力 ——「我能不能自己动手，而不是再许愿一次？」

| 项 | 内容 |
|---|---|
| 回答的问题 | 我能不能在这一段上直接写、写完就在稿子里、不排队不等 diff？ |
| 场景 | S06 |
| 缺了会怎样 | 入口存在但**要价不降**：作者仍要"选段→填意见→提交 job→等→看 diff"，本质是把自己的判断翻译成提示词，再赌一次生成。`T_接管` 不降反升，因为翻译+等待是纯开销。这就是 `T_接管 = ∞` 的现实形态。〔断点 8、原话 6「说不清楚自己想要什么」〕 |
| 与三条件的关系 | **C1 的完成条件**（C1 要求的是"能接管"，不是"能提交请求"）。 |
| 关键约束 | 就地改必须**同步、同屏、立即落盘**。异步 job + 等待 + diff 是这一层要取消的形态，不是要优化的形态。〔断点 8 判据②〕 |

### L3 · 局部化能力 ——「我改了这一处，系统还被迫重做多少？」

| 项 | 内容 |
|---|---|
| 回答的问题 | 改这一处，会不会牵动别处的字？会不会触发整章重排、全书重出？ |
| 场景 | S07、S10、S03 |
| 缺了会怎样 | **C2 不成立，BROE 停在"章"**。这是本产品的核心病灶：改一处 → 整章重生成 → 重生成比自写还贵 → 作者干脆不动。补长一章的代价（218–288 万 token、40 分钟–4 小时 40 分、3/3 未成功）就是这个半径的账单。〔断点 3/6、§2.4〕 |
| 与三条件的关系 | **C2 的唯一承载层，主指标 BROE 的执行者。** |
| 关键约束 | 本层不只是"少花钱"，是**让作者敢动**。半径大 = 不敢动 = 前面两层白做。 |

### L4 · 可信能力 ——「我看到的就是最终会印出来的吗？」

| 项 | 内容 |
|---|---|
| 回答的问题 | 系统说这章完成了，是真的吗？我的 7000 字去哪了？我改完之后，导出的是最新那版吗？ |
| 场景 | S02、S08、S09、S11、S15 |
| 缺了会怎样 | **C3 不成立**。三种撒谎同时存在：字数不足仍判 `ok`（10/10 章）、7000 字被压到 2400 字不告知、改了源稿成品悄悄过期。任一发生，作者就必须对**全部**产物重新人工核对，`T_接管` 被整体抬高——半径缩得再小也没用。〔§2.2、§2.3、断点 7/9〕 |
| 与三条件的关系 | **C3 的唯一承载层。** 同时是 L3 收益的兑现条件。 |
| 关键约束 | 这一层的产品语义是"**不许撒谎**"，不是"要更准"。一期只保证硬指标不说假话，不保证软判断准确。〔界定·5 本阶段不做 3〕 |

### L5 · 秩序能力 ——「我这一下，会不会和别处正在做的打架？」

| 项 | 内容 |
|---|---|
| 回答的问题 | 外部 Agent 在跑、我在 GUI 里改，两个动作同时发生会怎样？这一轮花了多少钱，能不能停？ |
| 场景 | S12、S13、S14 |
| 缺了会怎样 | 前五层的成果可被**一次并发静默摧毁**：跨进程锁只在一处调用，其余写路径裸写，"必炸"。更糟的是炸完没有痕迹——作者不知道自己刚才那次改是被覆盖了还是没保存。此时 L4 的"可信"变成一句空话。〔断点 10〕 |
| 与三条件的关系 | C1/C2/C3 的**保持条件**（不产生新价值，但缺了会让已产生的价值归零）。 |

---

### 1.1 六层与三条件、BROE 的对应

| 层 | C1 接管可发生 | C2 接管是局部的 | C3 产物可信 | 对 BROE 的作用 |
|---|---|---|---|---|
| L0 边界 | 前提 | — | 前提 | 不确定 |
| L1 定位 | **成立条件** | 前提（没有单位无法计量） | — | 从"章"里切出"段" |
| L2 就地 | **完成条件** | — | — | 不确定（但决定 `T_接管` 是否下降） |
| L3 局部 | — | **唯一承载** | — | **章 → 段** |
| L4 可信 | — | 兑现条件 | **唯一承载** | 防止收益被复核成本吃回 |
| L5 秩序 | 保持 | 保持 | 保持 | 防止归零 |

> 一句话：**L1 让"一处"存在，L3 让"一处"成为一个单位，L4 让这个单位可信，L2 决定作者愿不愿意用，L0 决定用的时候手里有没有东西，L5 决定用过之后还在不在。**

## 2. 功能结构

**「零 token 可验」定义**：不调用任何模型、只用仓库内已有的《潮汐档案》10 章文本 + 现有 `runs.db` 记录即可判定的部分。
凡涉及模型调用的功能，该字段写"不可零 token 验"，并给替代验法（验请求构造 / 验落点 / 验无新增 run），**不验效果**。

每条附「会失败的反证」：判据一旦放宽，这条必须变红。

---

### L0 · 边界能力

#### F01 · 本轮范围
- **一句话**：开工前指定这一轮只做哪几章（章数或章节区间），跑完就停，不多做一章。
- **场景**：S01
- **一期**：否（理由见 §4.3-Q3 的同源逻辑：一期要的是"接得住已经跑出来的稿"，不是"控制它跑多少"。现有《潮汐档案》10 章已足够验证接管闭环，一期不被"跑多少"卡住；但**这条必须在后续补上**，否则接管对象永远由系统单方面决定。）
- **零 token 可验**：不调用模型，直接比对"界面设定值 / workspace 新增章节文件数 / `runs.db` 本章节记录数"三者相等（S01 判据②③）。
- **会失败的反证**：只能选阶段、一跑就跑到所有未完成章 → 红。〔断点 1〕

#### F02 · 运行状态的真相（含"失联"）
- **一句话**：界面把"运行中 / 已停止 / 失联（最后一次活动：时间）"三态说清楚，且这个状态来自可核验的证据，不是界面自己的记忆。
- **场景**：S02
- **一期**：**是**（这是 Q2 的答案载体，见 §4.3-Q2）
- **零 token 可验**：杀掉后端进程，观察界面在超时后是否自己切到"失联"并显示最后活动时间；对照 `runs.db` 最后写入时间与章节文件 mtime。（不耗 token，只耗时间；超时阈值需实测。）
- **会失败的反证**：界面仍显示"运行中 3 小时 12 分"，而章节文件 mtime 已静止 → 红。〔断点 2、S02 判据②〕

#### F03 · 停止即保稿
- **一句话**：叫停之后，已完成的章全部保住、可打开；正在写的那一章留下为**残稿**，明确标"未完成"、不计入成品。
- **场景**：S03
- **一期**：**是**
- **零 token 可验**：在已有 10 章上启动第 11 章写到一半、按停止，检查 10 章文件字节未变、第 11 章以"未完成"标记存在、导出件章数为 10。
- **会失败的反证**：停止 = 当前章整章丢弃且无任何痕迹；或残稿被静默计入成品 → 红。〔断点 3〕
- **边界（重要）**：残稿只用于"看见损失了多少"，**不提供"从半截接着生成"**。从残稿继续写属于已否方向〔基线五·3〕，本文不采用。残稿可以被作者当作普通文本就地接管（走 F08），这是接管路径，不是续写功能。

#### F04 · 真暂停
- **一句话**：暂停意味着"不再产生新的模型调用、不再产生新的计费"，并且在暂停态里界面只提示在暂停态下做得到的事。
- **场景**：S04
- **一期**：**是**
- **零 token 可验**：暂停后 30 秒内检查 `cost_log` 无新增行、无新增产物文件；检查暂停态提示文案里不含"修改提示词后恢复"这类在暂停态无效的指令。
- **会失败的反证**：暂停只停显示、模型照跑照计费，提示语仍写"可修改提示词" → 红。〔断点 2、`nf_api.py:2878-2896`〕

#### F05 · 章间方向修正
- **一句话**：不停下整个运行，把一条方向修正注入到**后续章**的生成里，不产生新 run。
- **场景**：S05
- **一期**：**否**。作用域是"后面还没写的章"，与"接管已经写出来的稿"正交；且它需要一条运行中的写路径，与 F23 的单锁正面冲突，一期同时做会把锁的语义搅浑。
- **与已否方向的界线**：作用域是章与章之间，**不是**当前正在生成的段落，因此不是"边写边介入"〔基线五·4〕。
- **零 token 可验**：不可零 token 验。替代验法：提交后检查 `runs.db` 行数不变（判据③）+ 检查后续章的请求体里是否携带该修正（验构造，不验效果）。
- **会失败的反证**：修正提交后 `runs.db` 新增 run，或后续章请求体里查不到该修正 → 红。〔断点 4〕

### L1 · 定位能力

#### F06 · 段落视图
- **一句话**：一章以"可逐条指名的自然段清单"呈现，每条带章内位置与首句，作者能一眼扫到"第几段"。
- **场景**：S06、S07、S13
- **一期**：**是**
- **零 token 可验**：用现有 10 章文件生成清单，核对"清单条数 = 文件中自然段数"、"每条首句与原文逐字一致"。
- **会失败的反证**：清单里的"段"由模型切分、重开一次切点就变 → 红（段不再是指称对象）。

#### F07 · 指到即到
- **一句话**：点清单里的任一段，正文里对应那段立即被定位并进入可编辑态；反过来在正文里点到某段，清单同步高亮。两侧同屏，不跳页。
- **场景**：S06（判据①"全程在同一个页面内完成"）
- **一期**：**是**
- **零 token 可验**：在 10 章 fixture 上逐段点选，核对每次定位落到的文本区间与清单条目一致；核对"从指到一段到可以敲字"不发生页面跳转。
- **会失败的反证**：指一段要先切页签、或要点两次、或定位到段首而非该段 → 红。

---

### L2 · 就地能力

#### F08 · 就地编辑与即时落盘
- **一句话**：在这一段上直接改，改完即落盘、即刷新可见，不提交 job、不排队、不等待、不产生 run。
- **场景**：S06（判据①②③）
- **一期**：**是**（本功能的"是"，就是 C1 从"能许愿"变成"能接管"的分界线）
- **零 token 可验**：在现有章节上改一段，核对 ①`runs.db` 无新增行 ②文件内容已变 ③刷新/重开应用后内容仍在。
- **会失败的反证**：改完需要点"提交"、或需要等一个 diff 回来才生效、或重开应用后回滚 → 红。〔断点 8〕

#### F09 · 改写请求降为旁路
- **一句话**：原有的"选段→填意见→提交 job→看 diff"保留为**可选辅助**（作者说得出想要什么时用），但不再是改动某一段的唯一路径。
- **场景**：S06
- **一期**：**否**（保持现状，不改造；一期只保证 F08 这条主路径存在。改造它属于与 F09 同名的局部化问题，交给 L3。）
- **零 token 可验**：不可零 token 验。替代验法：验提交后产物落到**段**而不是整章（这是 L3 的判据，不是本功能的）。
- **会失败的反证**：提交改写请求后，整章被重写 → 红（此时它已不是"旁路"，是"唯一路径"的旧形态）。

---

### L3 · 局部化能力

#### F10 · 段是唯一的重算单位
- **一句话**：任何针对某一段的重算请求，只作用于该段；系统不得因为"某一段变了"而自行重算整章或全书。
- **场景**：S07（判据②）、S10
- **一期**：**是**（**本阶段最关键的一条约束**，见 §3）
- **零 token 可验**：手改一段后核对"未改动段落逐字 diff = 0"、"`runs.db` 无新增 run"、"成品未整体重出"。这三条都不花钱。
- **会失败的反证**：改一段触发整章重排、或触发全书重出成品 → 红。〔断点 3/6/9〕

#### F11 · 未改动区不变保证（可见的 diff）
- **一句话**：每次改动之后，界面能当场指给作者看"只有这一段变了，其余 N 段一个字都没动"。
- **场景**：S07（判据①）
- **一期**：**是**
- **零 token 可验**：改动前后对全书做逐字比对，核对"改动字符数 = 预期改动字符数"。
- **会失败的反证**：只给"已保存"而不给"哪里动了"；或 dif 显示为空但实际别处被改了 → 红。
- **说明**：这条的价值不是"给个 diff"，是**把 C2 变成作者自己能验的事**。作者不信系统的话，但他信"其余段落字节没动"。

#### F12 · 段增删后的位置稳定
- **一句话**：作者在一章里增加或删除自然段后，其余段仍然指得准——我上次标的那一段，增删之后还是那一段。
- **场景**：S06（就地改包含拆段/合段/删段）、S07
- **一期**：**是**（否则"就地改"只支持等长替换，作者一旦删段，F06 的清单就整体错位）
- **零 token 可验**：在一章中删掉第 3 段，核对原第 5 段仍能通过清单定位到原文同一句话。
- **会失败的反证**：删一段之后清单条目整体错位、A 段的标记跑到 B 段身上 → 红。
- **待研发确认**：位置稳定性靠什么承载（章内序号 + 内容指纹 / 其他）属实现选择，本文不定。**但产品要求是"增删之后还指得准"，不是"用某种 ID"。**

#### F13 · 段级重算失败不回退整章
- **一句话**：某一段的重算失败，只让这一段失败并可重试，不得把整章打回重来、不得丢弃该段原文。
- **场景**：S10（判据②）、S07
- **一期**：**是**（一期虽不做单段补长，但段级重算路径已存在，失败边界必须先画对，否则一次失败就把半径放大回整章）
- **零 token 可验**：断网/断模型后对一段发起重算，核对该段原文完好、其余段 diff = 0、可立即重试。
- **会失败的反证**：一次段级失败导致整章状态回退或原文丢失 → 红。

#### F14 · 单段补长
- **一句话**：某段太短时，只针对这一段扩写，不重跑整章。
- **场景**：S10
- **一期**：**否**（理由见 §4.3-Q3：补长当前 3/3 未成功〔§2.4〕，一期若承诺它，会把"判不达标"变成"判完更贵"。一期用"作者自己改"覆盖这条出路。）
- **零 token 可验**：不可零 token 验。替代验法：验请求体只携带该段及其必要上下文（验构造与成本量级，不验文本效果）。
- **会失败的反证**：补长一段的 token 量级与整章重写同阶 → 红（比值**需实测**）。

### L4 · 可信能力

#### F15 · 硬指标不说假话
- **一句话**：任一章字数低于配置下限时，其状态不得是 `ok`；质量分不得单独作为"合格"依据。
- **场景**：S08（判据①②）
- **一期**：**是**
- **零 token 可验**：以《潮汐档案》同口径回放——10 章各约 2.0–2.8 千字、下限 5000，核对 10/10 章被判"不达标"。**这条完全不花钱，且必须 10/10。**
- **会失败的反证**：出现任意一章"字数不足仍判 ok"，或"quality 8~9 使它看起来合格" → 红。〔断点 5、§2.2〕

#### F16 · 评分退出状态判定
- **一句话**：自评分可以继续显示，但它不再参与"完成/未完成"的判定；界面不得用高分抵消不达标。
- **场景**：S08
- **一期**：**是**
- **零 token 可验**：构造一章字数达标但评分低、一章字数不达标但评分高，核对前者的状态由字数决定、后者不得因高分转为合格。
- **会失败的反证**：评分仍能翻转状态 → 红。〔`stage4_writing.py:1132`〕

#### F17 · 判"不达标"之后有下一步
- **一句话**：被判不达标时，界面必须给出可执行的动作，而不是只亮一个红标。
- **场景**：S08（判据③）
- **一期**：**是**，但**只给两条**：**「我自己改」**（跳进 F08 的就地接管）与**「就这样接受」**（显式记录"作者已知不达标并接受"）。**不给「补长」**（见 §4.3-Q3）。
- **零 token 可验**：在 10 章不达标回放中，核对每章都出现这两个入口且点击后行为正确（跳转到该章首段 / 记录接受状态）。
- **会失败的反证**：只显示"不达标"而无任何入口；或"接受"之后状态仍被系统当作 `ok` 掩盖 → 红。

#### F18 · 字数变化的告知
- **一句话**：任一阶段使某章字数下降超过阈值时，界面必须当场说出来，并说明是哪一阶段、从多少到多少。
- **场景**：S09（判据①）
- **一期**：**是**
- **零 token 可验**：用 03 章（7184→2474）、05 章（7024→2257）的历史产物做回放，核对界面能否复现这两条告知。
- **会失败的反证**：7184→2474 静默发生、过程无任何提示 → 红。〔§2.3、断点 7〕
- **阈值**：**需实测**。测法：取《潮汐档案》10 章在各阶段间的字数变化分布，找"正常润色波动"与"被压掉 2/3"之间的空档；在拿到分布前，一期按"**下降幅度超过该章阶段前字数的某个比例即告知**"的形态实现，比值待回填。

#### F19 · 被压缩前的版本可回溯
- **一句话**：作者能看到"压缩前的稿子长什么样"，并选择最终用哪一版。
- **场景**：S09（判据②③）
- **一期**：**是**（只做"可看、可对比、可选定"，不做"自动判断哪版更好"）
- **零 token 可验**：在 03/05 章上回放，核对能调出 raw 与 refined 两版并逐段对照。
- **会失败的反证**：只能看到最终版、压缩前的版本不可达 → 红。

#### F20 · 成品过期标记与拦截
- **一句话**：源章节或任一项设定改动后，成品被标"过期"；"合并出 Word"和"导出"两个动作都必须因此拦截或要求显式确认，并能追到是哪一章/哪一项变了。
- **场景**：S11（判据①②③）、S15
- **一期**：**是**
- **零 token 可验**：改一个字符 → 核对成品标记亮起、导出被拦、提示指向该章。全程不调用模型。
- **会失败的反证**：docx 无 stale 标记，改完悄悄过期 → 红。〔断点 9、`judge.py:80` 有 stale 而成品无〕

#### F21 · 版本与来源可追
- **一句话**：界面能说清"当前这一版是谁、在什么时候、通过哪个入口改的"（GUI / 外部 Agent / 流水线），以及哪些改动发生在最近一次导出之后。
- **场景**：S13（判据②）、S15（判据②）
- **一期**：**是**（最小形态：章级"最后一次改动来源 + 时间"；段级只做"最近被改过的段"高亮，不做完整历史）
- **零 token 可验**：经由不同入口各改一处，核对这些改动在界面上的来源标记正确。
- **会失败的反证**：agent 改的和流水线改的在界面上无法区分 → 红。〔原话 2〕

#### F22 · 导出与源一致核对
- **一句话**：导出前后能核对"导出件逐章内容 = 当前源章节内容"，差异为 0 才允许作者做出"确认可用"。
- **场景**：S15（判据①③）
- **一期**：**是**
- **零 token 可验**：导出一份，对 docx 文本与源章节逐章逐字比对，差异须为 0。
- **会失败的反证**：导出件与源存在任何逐字差异，且系统未提示 → 红。

#### F23 · 外部 Agent 产物在 GUI 可见
- **一句话**：外部 Agent 通过 MCP 写入的产物，出现在 GUI 的章节列表里，标注来源，并可直接进入 F08 的接管路径。
- **场景**：S13

- **零 token 可验**：通过 MCP 入口写一个文件，核对它在 GUI 列表出现且来源标注正确。
- **会失败的反证**：产物只在 agent 侧可见、GUI 刷新后仍不出现 → 红。

## 3. BROE 的架构落点

### 3.1 问题本身

要让"改一处"不再强制重做整章，产品里必须先有**一个可以被单独指名、单独替换、单独核对的最小文字单位**。

当前产品里**不存在**这个单位。存在的只有"章"：章是文件的单位、是流水线阶段的单位、是评分的单位、是过期的单位、是导出的单位。所以"改一处"在产品语义上无处落脚，只能被翻译成"改一章"。

**这就是 BROE = 整章的全部原因，也是唯一原因。**

### 3.2 这个单位是什么

产品概念：**「可指名段」**——一段能被作者指着说"就是这一段"的文字，且具备四个属性。

| 属性 | 产品含义 | 缺了会怎样 |
|---|---|---|
| **有身份** | 前后增删文字之后，它指的还是它 | 作者标了 A 段，改完别处后 A 段的标记跑到 B 段身上 → 作者不敢标记，等于没有 |
| **有边界** | 边界是作者看得见的东西（自然段），不是模型自己切的 | 切点每次不同 → 每次打开都是新的一批"段"，无法累计工作 |
| **有来源** | 这一段是谁写的、过了哪几道工序、被谁改过 | 作者无法判断"这段是 AI 的原样还是我改过的" → 必须重读 → `T_接管` 回弹 |
| **有独立生命周期** | 它能在别处不变的前提下被替换、被重算、被核对 | 这是 BROE 的全部内容；没有它，"局部"没有计量单位 |

**注意：这不是数据库字段名，是产品承诺。** 研发用什么承载（章内序号 + 内容指纹 / 其他）本文不定，标**待研发确认**。产品只要求这四条行为成立。

### 3.3 有了它，哪些能力才成立

| 能力 | 没有"可指名段"时的真实形态 |
|---|---|
| 指到一处（F06/F07） | 只能指到"章"。**"某一处"在产品里不存在**，C1 无从谈起 |
| 就地改（F08） | 能改，但改完之后系统不知道改的是"哪一处"，只能认为"章变了" |
| 只重算这一处（F10） | 不可能。重算的触发单位是章，所以最小半径是章 |
| 证明别处没动（F11） | diff 没有对象。只能给"整章新 vs 整章旧"，作者仍需逐字读完 |
| 段级补长（F14） | 只能整章重跑。这就是 218–288 万 token、3/3 失败的来源 |
| 压缩可见到段（F18/F19） | 只能到"这一章从 7184 变成 2474"，说不出哪几段被压掉了 |
| 来源标注到段（F21） | 只能到"这一章被 agent 改过"，作者仍要通读全章 |
| 段位置稳定（F12） | 增删一段即全线错位 |

### 3.4 没有它，哪些能力只能做成假动作

必须点名，因为这是最容易糊弄过去的地方：

1. **"段落高亮 + 提交改写请求"** —— 看起来是段级操作，实际是一次整章重生成后取其中一段贴回来。作者看到的是"段变了"，实际付的是整章的账，且别处也被重写了。**这是假动作。**
2. **"段级 diff"** —— 若 diff 的两侧来自两次独立的整章生成，那 diff 里显示"只有这一段变了"是巧合，不是保证；下一次就会显示几十处无关变化。**这是假动作。**
3. **"段级过期标记"** —— 若段没有身份，段级 stale 无法计算，只能退化成章级再靠界面装作很细。**这是假动作。**
4. **"停止保住半截"** —— 若半截不是以可指名的段存在，它只是一坨文本，作者接不了手，等于没保住。

### 3.5 它会让哪些现有能力必须让步或改变语义（全部标「待研发确认」）

| 现有能力 | 语义必须怎么变 | 状态 |
|---|---|---|
| 八阶段流水线以"章"为工作单位 | 阶段 4/5/6 的产出必须能携带段的身份；否则下游一接手就把段信息丢掉，BROE 又回到章 | **待研发确认**（是否可在不改阶段划分的前提下做到） |
| 段落修 job（`ParagraphRefinePanel.vue`） | diff 的对象从"章"变为"段"；一次 job 的产出必须落回同一个段身份 | **待研发确认** |
| `judge` 的 stale 口径指纹（章级） | 是否下沉到段、还是保留章级只在界面提示到段 | **待研发确认** |
| 合并出 Word（按章拼接） | 拼接后段身份是否仍可追；导出件里是否需要保留段标识 | **待研发确认** |
| 停止 = 丢整章 | 变为"丢最后未完成的段"；已完成的段必须无损 | **待研发确认** |
| quality 评分（按章） | 一期不新增段级评分（避免制造新的不可信判定）；评分下沉到段属后续问题 | 本文明确不做段级评分 |
| 断点续跑 / 恢复 | 恢复的最小单元从"章"变成"段" | **待研发确认** |
| MCP 写入契约 | 外部 Agent 写入时必须声明写的是哪一段，否则系统无法维护段身份 | **待研发确认** |

### 3.6 一期是否必须动它

**答：必须动，但只动一半——动"重算与核对的粒度"，可以先不动"全书唯一身份"。**

具体来说，一期取**「章内可寻址」的过渡形态**：

- 段身份**只在章内有效**：由"章内位置 + 内容指纹"共同确定，不跨章、不要求全书唯一。
- 但有一条**硬约束必须先立起来**：**任何重算请求的最小触发单元必须是段，不得是章。** 这是 F10，一期必须成立，不允许"先按章实现、以后再收窄"——因为"以后再收窄"就是本期最大的假动作来源（§3.4 第 1、2 条）。

**取舍与代价（必须写明，不许含糊）：**

| 取舍 | 得到的 | 付出的代价 |
|---|---|---|
| 不做全书唯一段身份 | 一期不必以数据层重构为起点（该顺序已被否〔基线五·5〕） | ① 跨章能力只能到章：全书检索定位、跨章 diff、跨章"这一段被哪一章引用"都做不了；② S13 的"agent 改了什么"只能说到"哪一章的第几段"；③ S11 的过期标记精确到章，不到段 |
| 用"章内位置 + 内容指纹"承载身份 | 不需要存量迁移（47 run / 393 个章节文件不动） | ① 章内大幅增删时指纹可能失配，需要 F12 兜底（**待研发确认**失配率）；② 章被整章重生成后，旧段的身份全部失效——这是可接受的，因为整章重生成本来就是"重来"，BROE 已经如实反映为"章" |
| 一期不承诺"AI 参与的段级重算"效果 | 一期验收只用**作者手改**这条零成本路径证明 BROE 到段 | BROE 的"段"在一期只对"作者自己改"完全成立；对"让 AI 改这一段"只承诺"请求只作用于该段"，**不承诺质量与成本量级**（后者 **需实测**） |

**为什么这个取舍是对的（一句话）**：一期要证的是"作者能接住"，不是"系统能全局寻址"。前者只需要段在**当下这一章里**是一个可靠单位；后者是全书级的能力，它可以在段已经是可靠单位之后再长出来，反过来不行——如果先做全书身份而没有"段是唯一重算单位"这条约束，做出来的仍然是一个能全局定位、但一改就整章重算的系统，BROE 一点没降。

## 4. 一期范围

### 4.1 一期的通过判据

> **一期结束时，作者能在不重建流水线的前提下，完成一次完整的接管。**

拆成四步，四步全绿才算通过：

| 步 | 作者要做的事 | 必须存在的功能 | 判据（可判定） |
|---|---|---|---|
| ① 找到一处 | 在已有稿里指到某一段 | F06、F07 | 从打开章到"该段可编辑"，同屏、不跳页 |
| ② 就地改 | 在那一段直接写，保存 | F08 | 零 job、零等待、零新 run；刷新/重开不丢 |
| ③ 确认没伤到别处 | 看到"只有这一段变了" | F10、F11 | 未改动段逐字 diff = 0；无新 run；成品未整体重出 |
| ④ 拿到与源一致的成品 | 导出并确认 | F20、F22 | 导出件与源逐章差异 = 0；过期标记已清；该状态不被静默推翻 |

**这四步里没有一步需要"AI 写得好看"。** 这正是它可以在质量恒为负的前提下被验证的原因。〔界定·3、§5 本阶段不做 6〕

**一期不做（否）**：F01、F05、F09、F14、F23、F27 —— 共 6 项。

- **让"一处"是一个单位**：F10/F11/F13（L3，主指标的唯一承载）
- **让"看到的"是真的**：F02/F03/F04/F15/F16/F17/F18/F19/F20/F21/F22（L4+L0）

### 4.3 业务分析师抛回的四问

#### Q1 · BROE 从"章"降到"段"真的成立的可测判据

**总原则**：BROE 不靠"作者感觉"，靠**三个可数的量**。三个量都不需要模型调用，因此不会被"他读不下去"卡住。

**必测点 A（零成本，一期验收主判据）**：在《潮汐档案》10 章 fixture 上，于 GUI 内做**一次纯手改**（替换某一段中的若干字），测三个量：

| 量 | 定义 | 通过 | 不通过 |
|---|---|---|---|
| ΔT | 该动作前后 `cost_log` 的新增 token 之和 | ΔT = 0 | ΔT > 0 → 说明"手改"仍触发了模型重算 |
| ΔD | 全书其余所有段落改动前后逐字比对的字符差异数 | ΔD = 0 | ΔD > 0 → 波及别处 |
| ΔR | 该动作前后 `runs.db` 的 run 数增量，以及成品是否被整体重出 | 0 且未重出 | 任一 > 0 |

**三档判定（二值，无灰区）**：

- 三项全绿 → **BROE = 段**
- ΔD > 0（波及同章其它段）→ **BROE = 章**
- ΔR > 0 或成品整体重出 → **BROE = 全书**

**必测点 B（成本量级，需实测，非一期验收门槛）**：对同一段的"AI 重算"，分别用"整章重跑"与"单段重算"，各跑 N 次（N **需实测**确定），比较 token 中位数。

- **阈值需实测**：当前**没有**任何实测比值可以引用，因此本文**不给阈值**。
- **测法**：固定同一章同一段、同一提示词，交替跑，记录 `cost_log`；取中位数比。得到比值之前，一期只承诺"请求只作用于该段"（可验请求体），**不承诺**比值落在某个区间。
- **为什么不能先拍一个阈值**：一旦拍了，它就会变成"看起来达标"的数字，而这正是 `chapter_log` 在 10/10 章不达标时记 `ok` 的同一种错误。〔§2.2〕

**反证（判据放宽该变红的地方）**：如果"BROE = 段"的判定允许"ΔD 很小"或"ΔT 只是少量"，那它立刻失去判别力——因为当前的整章重写在多数情况下 ΔD 也不大（只有被改的那章变了）。**所以 ΔD 必须是 0，ΔT 必须是 0，不允许"接近 0"。**

#### Q2 · 作者不用终端，"进程已死"如何由 GUI 自己说出口

**产品形态：三态，不是二态。**

| 状态 | 界面文案 | 判定来源（必须是证据，不是界面记忆） |
|---|---|---|
| 运行中 | 「运行中 · 本章已写 1,240 字 · 最后一次活动 2 秒前」 | 后端心跳 + `runs.db` 最近写入 + 产物 mtime，三者在刷新窗口内 |
| 已停止 | 「已停止（你于 14:32 叫停）· 已保住 10 章」 | 收到停止确认，且三个证据源均静止 |
| **失联** | 「**失联 · 最后一次活动 15:04（已 12 分钟无响应）** · 常见原因：进程已退出」 | 任一证据源超过超时窗口无更新，或 SSE 连接已断 |

**四条硬规则：**

1. **优先显示"最后一次活动时间"，不优先显示推算时长。** 现在的"运行中 3 小时 12 分"是从开始时间减出来的，它会撒谎——进程死了它照样在涨。改成"最后一次活动 xx:xx 前"，作者一眼能看出冻结。〔断点 2、S02 判据②〕
2. **"失联"必须由 GUI 主动说出，不能等作者发现。** 证据源超时即切态，不需要作者点任何东西。
3. **提供"标为已停止"这一个动作。** 作者在失联态点它，系统进入可接管状态（章的写锁释放、可编辑）。若进程其实还活着并继续写，必须报**冲突**（走 F24/F25），不得静默让两边都写。
4. **不许自动"复活"。** 一旦标为已停止，除非作者再次启动，界面不得自行回到运行中——否则作者会再次失去对"哪个是真的"的判断。

**超时窗口**：**需实测**。测法：记录正常运行时心跳/写入的最大间隔（取《潮汐档案》多次 run 的间隔分布上界），窗口取该上界的若干倍；在拿到分布前，窗口值待回填，**不写死一个数字**。

**反证**：界面显示"运行中"、章节文件 mtime 已静止、作者手动刷新后仍显示运行中 → 红。

#### Q3 · S08 判"不达标"后三条出路，哪一条一期必须

**答：必须的是「修改」和「接受」。「补长」一期不必须。**

理由（三条，逐条落在已定前提上）：

1. **判"不达标"这件事本身不能增加作者的成本。** 一期一旦把"补长"作为唯一出路，就等于：系统第一次说了真话（这章不达标），紧接着把作者推进当前最贵的路径——单章补长 218–288 万 token、40 分钟–4 小时 40 分、3/3 未成功〔§2.4、断点 6〕。这会让他学到"别让系统判我不达标"，反而去关掉判定。**判定必须廉价，否则判定会被绕过。**
2. **「修改」就是接管路径本身。** "我自己改"是 F08，它已经在册、已经零成本、已经可验。判不达标 → 点进去 → 就地改，这条链不需要任何新技术。
3. **「接受」必须在一期，因为它是"作者署名"的前提。** 他的质量基线是恒为负且自愿接受〔原话 7〕。如果系统只允许"达标"和"重做"两种结局，那他在本产品里永远无法把一章定稿——而一期要的正是"确认这一版是我的"〔S15〕。所以"接受"必须是一个**显式的、被记录的状态**：它不是 `ok`，它是"作者已知不达标并认了"。

**一期形态：**

- 「我自己改」→ 跳 F08（就地接管）
- 「就这样接受」→ 写入一条显式状态（不达标 + 作者接受 + 时间），且该状态**不得被后续流程静默推翻**（要推翻必须告知，见 F20/F22）
- 「补长」→ 一期不提供。**产品上不出现这个按钮**，优于"出现但点了没用"。

**反证**：如果一期出现"补长"按钮而它背后仍是整章重跑，那么 S08 的判据③就变成了"给了一个更贵的坑"，这条必须变红。

#### Q4 · 并发口径：四个写入入口是否全部纳入同一把锁

**答：全部纳入，且"接不上的入口必须被禁用，不允许裸写"。**

产品口径只有一句：**同一份稿，同一时刻只有一个写入者。这与入口有几个无关。** 〔S12、断点 10〕

一期落地口径（三条）：

1. **四个入口（GUI / HTTP / MCP / CLI）对同一份稿的写操作，走同一把互斥。** 不接受"GUI 有锁、agent 加锁、CLI 裸写"这种按入口分治的做法——那等于锁有后门。
2. **后到者被明确拒绝**，且提示可读（F25：谁在写、写到哪、你可以等或可以停）。**不允许**"排队等待"作为一期默认，因为等待会让作者以为自己在改、实际在排队，一旦排队很长他会重开一个入口——那正是"必炸"的由来。
3. **若某入口在一期内无法接入这把锁（待研发确认），产品上必须把它显式禁用**（不可达、或写操作直接拒绝），而不是"先放着"。理由：一个绕锁的后门，会让 F24 的"S12 判据②损坏次数 = 0"永远无法成立，而这恰恰是一期唯一一条"归零型"判据。

**关于 CLI 的特殊说明**：作者永不用终端〔基线·使用者〕，因此 CLI 在产品上不是用户路径。但它在技术上是一台写入入口，**所以它同样必须持锁；若接不上，就禁用**。"用户不用它"不等于"它不会写"。

**关于读操作**：本口径只约束写。读（浏览、看成本、看状态）不需要持锁，否则 F02 的状态面板会被锁住而无法反映真相。

**反证**：一期若宣称"已解决并发"，但仍存在任意一条不持锁的写路径能改到同一份稿 → 红。

### 4.4 一期结束时，仍然是红的（必须先说清楚）

诚实列出，避免被当成"没做完"：

- **产物仍然读不下去是允许的。** 一期不改善文本质量，只保证"读不下去时有处下手"。〔界定·5 本阶段不做 6〕
- **AI 参与的单段重算，成本量级未验证。** 一期只验"请求只作用于该段"，不验"多便宜"（需实测）。
- **跑多少仍不受控**（F01 不做）。一轮可能仍跑向所有未完成章。
- **运行中改不了方向**（F05 不做）。
- **外部 Agent 的产物在 GUI 里仍偏黑**（F23 不做），但至少不会破坏数据（F24）。
- **预算超限仍可能不拦**（F27 不做），只做到"花多少看得见"。
- **段身份只在章内有效**，跨章能力到章为止（§3.6 的代价）。

## 5. 明确不做

### 5.1 一期绝不做（会被误以为"顺手就该做"的）

| 不做 | 因为它是 | 若做了会怎样 |
|---|---|---|
| **重做编辑器** | 不是本产品的问题 | 语法高亮、富文本、多标签页、双向同步、vim 键位 —— 这些提高的是"打字舒适度"，不是"能不能改某一段"。作者的原话是"什么都点不了"，不是"编辑器不好用"〔原话 1〕。**一期只要"点得到 + 敲得进 + 存得住"，其余一律不做。** |
| **文本质量优化** | 已被否〔基线五·1〕 | 换模型、调提示词、加评分维度、做"润色更好"——质量已被设为常量并由作者自愿接受〔原话 7〕，它在判定式里不进分子也不进分母〔界定·3〕。 |
| **数据层重构** | 顺序已被否〔基线五·5〕 | 不做全书唯一段身份迁移、不做 47 run / 393 个章节文件的存量回填、不重建存储。一期只为 F10 做**最小**改动（段成为重算单位），标**待研发确认**。 |
| **重写八阶段 / 加第九阶段** | 〔界定·5 本阶段不做 1、2〕 | 八阶段是既成事实，一期只在上面打通接管；不新增"人工精修阶段""审校阶段"。 |
| **生成中持续在场（共写）** | 已被否〔基线五·4〕 | 与"就是快"直接冲突，且与作者的时间预算冲突（他不能守在旁边）。一期只在 AI **停手之后**接管〔界定·1〕。 |
| **半截可编辑 + 续写** | 已被否〔基线五·3〕 | F03 只把残稿留作"看见损失"，**不提供从半截继续生成**。 |
| **跑一章让人读一遍作验收** | 已被否〔基线五·2〕 | 一期所有验收判据都是可数的（ΔT / ΔD / ΔR / 10/10 章判定），不依赖"他读不读得下去"。 |
| **引擎选型** | 产品负责人的决定〔§2.4 原注〕 | 本文不提 hermes 与直连的取舍。 |
| **多人协作 / 账号 / 云同步 / 发布分发** | 只有一个作者〔界定·5〕 | —— |

### 5.2 一期做，但容易被误以为"应该顺带做"的边界

| 看起来要做 | 一期实际做到哪 | 为什么停在这 |
|---|---|---|
| **段级过期（stale）** | 只做到**章级过期 + 指向章内位置** | 段身份只在章内有效（§3.6），精确到段的 stale 需要全书身份；一期做了就是假精确 |
| **段级质量评分** | **不做**。评分退出状态判定，只显示不决策（F16） | 段级评分会制造新的"不可信判定"，与 F15 的方向相反 |
| **自动修好** | **不做**。只做"我能改"，不做"改对" | "改对"是质量优化，已否 |
| **全书检索 / 跨章定位** | 不做 | 需要全书身份，属 §3.6 已列的代价 |
| **跨会话撤销/重做** | 一期只做"本次打开应用内的改动可见与可比"（F11），不做完整 undo 栈 | 完整 undo 栈要先有稳定的改动单位与历史承载，**待研发确认** |
| **接管后自动重跑下游全部阶段** | **不做，且必须不做** | 这正是"改一处 → 整章/全书重做"的复发路径。一期要求下游**不自动**重跑；要重跑必须作者显式发起，且重跑单位是段 |
| **"接管完成"的自动判定** | 不做。只有作者显式"确认可用"（F22） | 自动判定就是让系统替作者署名，而系统的判定已被证明会撒谎〔§2.2〕 |

### 5.3 一条贯穿性的不做

**不做"看起来像接管"的东西。**

判据很简单：**如果一个功能让作者觉得"我改了这一段"，但系统实际重做了整章——那它就必须被砍掉，无论它多好看。** 这是 §3.4 列的四条假动作的共同特征，也是本产品过去一直"有功能但没有入口"的根源。
