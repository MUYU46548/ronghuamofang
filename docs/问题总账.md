### 设定的时期与演变（2026-11-12，第 8 条）

**病**：条目字段里没有时间维度，于是"早期外观可见、后期收进皮下"这类设定**两种写法都错** ——
挤进一句话会被冲突检查按字面判成矛盾（写对了还挨红），拆成两个不同名条目则永不互相比对
（错的那条也看不见）。根因不是提示词不好，是**没有地方存"第几期"**。

**写法**（都是可选的，两栏都空着 = 与改动前完全一样）：

| 键 | 用途 | 例 |
|---|---|---|
| `period` | 这条设定只在哪一期成立 | `"period": "战后"` |
| `phases` | 同一个东西分期不同状态 | `[{"era": "早期", "note": "外观可见"}, {"era": "后期", "note": "收进皮下"}]` |

读法只有一份：`setting_schema.normalize_period`（认 `period`/`era`/`时期`/`时代`/`阶段`，
认 `phases` 的字符串数组写法，也认把 phases 错写进 `period` 的情况）。

**四个消费点**：

1. **写作注入**（`build_character_card` / stage4 `_render`）：分期分点列出，写明"只写本章所处
   时期的那一版"；本章大纲出现某个时期名 → 那一期标 `← 本章大纲提到这个时期`；
   大纲没提时期 → 明说"判不出来就取最早那一期，别把状态写成永恒不变"。
2. **冲突判定**（`material_state.detect_conflicts`）：只在**同一时期**桶内比较；
   卡上的 `时期` 字段本身不参与比对（否则"早期 vs 后期"会被判矛盾）。
3. **演变清单**（`detect_evolutions`）：跨期差异单列，**不判红**；任一侧没标时期 → `suspect=True`
   + 写出是哪张卡没标（"判不出是演变还是矛盾"）。进 `merge_audit.json`、
   `material_review.py` 报告与 `GET /setting/conflicts` 的 `evolutions`。
4. **版本对照 / 溯源**：`setting_versions` 与 `setting_provenance` 的字段表都加 `时期`，
   取数走 `period_cell`（否则条目写作 `时期` 时对照会说"没改"）。

**界面**：设定页签的条目抽屉里加两栏 —— “时期”（单行）与“演变”（每行一期，`时期：状态`），
存回 JSON 就是 `period` / `phases`。手册同批改了（`console/src/help/07-setting.md`）。

**提示词**：`prompts/stage1_materials.md` 补了 `phases` 写法与"别塞一句话、别拆两个条目"的说明
（**只追加在模板尾部**，不改任何既有段落；`prompts/factory` 已同批同步）。
存量项目不会自动获得时期 —— 归并出来的条目本来就没这个信息，得作者在抽屉里填，
或在重跑阶段 1 前把素材按时期写清。

**兼容性红线**：没写时期的条目，注入文本、冲突清单、`audit()` 输出形状与改动前**逐字一致**
（用例 E 组守着）。形状上只多了 `evolutions` / `evolution_count` / `evolution_suspect` 三个键。

判据：`tests/unit/test_setting_period.py`（40 条：A 九种写法归一 / B 注入规则 / C 冲突与演变 /

单条上限 `FULL_TEXT_CAP=20000`（超了写明“余 N 字没进”，不静默）；总预算提到 200000；
超预算**打印告警**而不是悄悄丢掉。

判据：`tests/unit/test_full_text_injection.py`（16 条，含“第 400 字之后的内容也在注入里”）。

边界：**只有 vault 来源的条目带 `body`**。stage1 模型归并出来的设定条目本来就没有原文，
仍走 snippet —— 那不是被截断，是从来就没有。

### 关系不再丢：抽 `[[链接]]` + 一跳扩散（2026-11-11）

用户问“模型是不是根本不会举一反三”。不是不会，是**关系在两处被扔掉**：

1. 扫描时 `re.sub(r'[#*`\[\]]', '', body)` 把 `[[阿禾的师父]]` 变成纯文字，链接语义消失；
2. 注入只判“条目名有没有出现在本章大纲”，**一跳都不扩**。

现在：

- `obsidian_bridge.extract_wikilinks()` 从正文抽 `[[目标]]` / `[[目标|别名]]` / `[[目标#小节]]`，
  三类条目都存 `links`；
- `stage4_writing._expand_links()` 做**一跳**扩散（只一跳：两跳会滑成“整个设定集都相关”，
  等于没筛，也吃光预算）；
- 世界条目与角色卡都带关联项，且**明确标注“关联项，未必在本章出场”**（不冒充本章事实）。

判据：`test_full_text_injection.py` 的【F】组（抽链接三种写法、去重保序、扫描带 links、
关联项进注入且有标注、**两跳之外的条目不进**）。

未做：关系图（用户明确说 c 后续单独做，工程量在 GUI）。

### 过程可见：执行方心跳（2026-11-11）

用户原话：“踢一脚跑一下 —— AI 干活时你看不见它走到哪步、卡在哪。”
`progress.json` 只有阶段状态，没有“现在在做什么”，更没有“多久没动静”。

现在：

- `utils/activity.py`：`beat(root, kind, target, note)` 写 `data/state/activity.json`；
  文件即状态，最近动作只留 50 条；**“卡没卡住”由读方算**（`idle_seconds`），不信写入方自述。
- `GET /activity`（读侧不拦）、`POST /activity/beat`（**agent 也能写**：这是记录不是审批）。
- `nfctl beat write "第 3 章" --note "写 raw/03.md"` / `nfctl beat-status`（不启服务）。
- 界面左栏底部一颗药丸：`● 写产物 · 第 3 章 · 15 秒前`；超 180 秒转黄
  `● 读资料 · 设定集 · 8 分钟前`。**只提示，不阻断**（离线跑批不该被拦）。

判据：`tests/unit/test_activity.py`（15 条，含“把心跳造旧 5 分钟 → stale、idle 在 280~320 秒之间”）。
真机目检：两种状态都截图看过（绿 / 黄）。

未做：心跳超时后的**主动出声**（弹窗/邮件）——现在只是界面变黄。执行方要不要自动化上报
（比如流水线每完成一章自动 beat）也没接。

**补上（同日，作者要求两条都要）：**

- **自动上报**：`stage4_writing` 的段群落盘回调里自动 `activity.beat("write", "第 N 章", "盘上已写 M 字")`，
  **同章 30 秒最多一条**（每群一次会把 activity.json 刷爆）。写作过程中界面就能看到“在写第几章、多少字”。
- **主动出声**：复用已有的系统通知通道（`window.mofangAPI.notifyGate` → `notify:gate`，主进程 `Notification`，
  不用改 Electron）。
  `activity.stale` 由正常转超时时弹一次，之后**每 10 分钟最多一次**（前端 2.5 秒刷一次 /activity，不节流会刷成瀑布）。
  ⚠️ 这条**没有真机验**：系统通知要真 Electron 窗口，headless Chromium 里的垫片不弹。

判据：`test_activity.py` 的【F】组（自动 beat 存在且带节流、前端调 notifyGate 且带节流）——
是**源码断言**，不是行为断言；真正的行为验证要跑一次 stage4（要模型）。

## 维护纪律（硬）

1. 每完成一项，**同一笔改动里**改这里的状态并写判据；只改代码不改账 = 账变成新的谎。
2. 新增条目必须写"出处"（谁提的、哪份文档哪一句），否则不许进。
3. 只有两种状态可以写进"已完成"：**用户实际用过并认可**，或**有一条会失败的判据守住**。其余一律"未验"。
4. 旧台账（`承诺台账` / `收口台账` / `roadmap` / 各类日期清单）**不再新增内容**，只做历史索引；本条一旦破例，本账就变成第 44 篇废纸。
