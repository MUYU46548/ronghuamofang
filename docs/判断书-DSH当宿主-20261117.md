# 判断书：DSH 当宿主，墨坊当尺（2026-11-17）

> 依据暮雨 2026-11-17 的三条修正：① DSH 能写书不必验（已有大量魔改整合包在用）；
> ② 真风险是**插件 API 与宿主版本都在变**；③ 账本模型取决于**和 DSH 集成多深**。

## 一、已划掉的问题

- ~~DSH 能不能写书~~：不验。能力面已被现成整合包证明。
  残余风险只剩一条：**写出来过不过墨坊的判据**——那正好归墨坊，不归 DSH。

## 二、真风险：插件与宿主一起漂（U2）

DSH 仍是 `0.2.2-rc.3`；插件 API 与宿主形状都会变。这不是能消除的风险，只能**限制爆炸半径**。

四条限损（方寸侧已验证过的做法，直接照搬）：

1. **把不可控层做薄**：插件 ≤300 行，只依赖两个宿主接口（`ctx.tools.register`、`ctx.webServer.register`）。
   所有业务逻辑（判据、三层稿、Word、成本）留在墨坊 HTTP 侧。
   → 宿主改形状时，重写的是薄层（几小时），不是业务。
2. **只设下限，不设上界**：`engines.dsh` 写上界会让升级后插件**静默消失**（方寸踩过）。
3. **探针 + 明确降级**：启动时 `checkHost()`；宿主没有所需服务 → **明说“接不上”**，不假装能用。
4. **契约版本独立于宿主版本**：插件与墨坊之间带 `CONTRACT_VERSION`；墨坊改字段就 +1，
   插件按版本决定能不能调、怎么调，不靠猜。

## 三、账本模型取决于集成深度（U3）：四级谱系

| 级 | 集成形态 | 书的账本在哪 | 代价 | 可逆性 |
|---|---|---|---|---|
| L0 | 只读：DSH 查状态/章节/成本 | 方寸卡 + 墨坊工作区（现状） | 零改动 | 随时回退 |
| L1 | 工具级：模型能调 改章/精修/跑阶段/出 Word | 同上，章级动作有回执 | 薄插件（≤300 行） | 删插件即回退 |
| L2 | 会话级：方寸派单 → DSH 开书会话，上下文包 = 书 + 章 + 判据 + 上一章结尾 | **书的账本进方寸**（一卡一书，一章一派单/回写） | 需要“章级账本”设计 + 派单模板 | 中度，需设计回滚 |
| L3 | 宿主级：DSH 当主界面，墨坊退成纯工具服务 | 工作区即账本，方寸只记书级任务 | 重做界面语义（判定/审稿/精修/成本谁显示） | 低（等于换产品） |

## 四、建议的推进顺序

1. **L1 起步**（薄插件 + 一张 health）：目的不是“把功能搬进去”，而是**看模型会不会用判据**
   —— 它会不会在改章前先查字数/退化/节级判据，还是照着感觉改。这一步就能证伪“尺有用”。
2. **L2 是真正的拐点**：只有 L1 观察到“模型确实在用工具”（不是靠提示词求它），才值得设计章级账本。
3. **L3 等两本书跑通再谈**：那时才清单化“哪些页面 DSH 里没有对应物、要不要重建”。

## 五、退出条件

- L1 跑一周，模型调用工具的比率低（多数动作仍是自由发挥）→ 说明“工具 + 宿主”不解决问题，回到“人点界面 + 墨坊自己跑”。
- 宿主两次升级都要求改插件形状 → 薄层成本超过收益，停在 L0。
