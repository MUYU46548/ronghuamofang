# 升级与书稿迁移（跨版本承诺书）

回答那个「现有文档没有答案」的问题：**我自己的书稿，跨版本怎么迁移？**

一句话：升级会刷新**程序**，绝不动**书稿**；书稿结构若真需要变，程序会在启动时
先打快照再自动对齐，对不齐就**明确拒绝运行**，绝不静默写坏。

---

## 一、三样东西，三个版本号

| 东西 | 版本标记 | 谁负责刷新 | 在哪 |
|------|----------|-----------|------|
| 桌面程序本体 | `console/package.json` → 安装包版本 | 安装 / 自动更新 | 安装目录 |
| **代码与提示词**（`scripts/` `prompts/` `templates/`） | `SEED_VERSION` ↔ 工作区 `.seed-version` | `seedWorkspace()`（启动时） | 工作区 |
| **书稿数据**（`data/`：设定集、大纲、章节、进度、归档） | `DATA_SCHEMA` ↔ `data/state/workspace_schema.json` | `utils/workspace_migrate`（启动时） | 工作区 |

前两行以前就有，第三行是本次补的机制（C3）。三者**各自独立**：改提示词只需 bump
`SEED_VERSION`；改数据结构才需要动 `DATA_SCHEMA`。

## 二、升级一次，实际会发生什么

1. **代码与提示词**：`.seed-version` < `SEED_VERSION` → force 覆盖
   `scripts/` `prompts/` `templates/`。**改过的提示词会被新版覆盖**，这是刻意取舍：
   与新程序不兼容的旧提示词比「丢失自定义」危害更大。
2. **配置**（`config/`）：**只补缺、绝不覆盖**。文件不存在才从随包里复制；
   已存在的文件（书名、模型选择、你的风格笔记）一个字节都不动。
   新版新增的 provider 不会自动并进你的 `system.yaml`（键级合并要改写用户配置，
   风险大于收益）——要用就手工把随包里那段贴过去。
3. **书稿**（`data/`）：正常情况下**什么都不做**。启动时只做一次结构对齐检查：
   - 戳缺失（老工作区 / 新装）→ 记基线 v1，**不碰任何数据**；
   - 戳与代码一致 → 无事；
   - 戳落后且有迁移步骤 → **先打快照**（`import_guard` 契约），再逐步执行；
   - 戳比代码还新（降级 / 用旧版打开了新版写的书）→ **拒绝运行**。

## 三、迁移长什么样

```
$ python scripts/data_migrate.py            # 状态（只读，默认）
[migrate] 代码期望数据结构 v3；工作区 已记为 v1 …
[migrate] 数据 v1 → v3：待跑 2 步（其中 1 步需人工确认 --yes）

$ python scripts/data_migrate.py --dry-run  # 预演：跑哪几步、打不打快照
$ python scripts/data_migrate.py --run      # 执行 safe 步骤（补字段 / 建索引类）
$ python scripts/data_migrate.py --run --yes # 连同会改写你文件结构的步骤
```

- **先快照后动手**：真迁移前落 `history/<时间戳>_before_workspace_migrate`，
  报告里带可直接抄的回退命令 `python scripts/snapshot.py --restore <ID> --yes`。
  快照失败 = 迁移一个字节都不执行（fail-closed，与丙3 同一条契约）。
- **只自动跑 safe 步骤**：启动时（桌面端 / `orchestrator`）只跑「补字段、建索引、
  补默认值」这类不删不改你内容的步骤。会改写文件结构的必须 CLI 显式 `--run --yes` ——
  机制可以自动，动用户的东西不行。
- **失败不推进版本戳**：停在第几步就留在哪个版本，下次启动重试同一批步骤，
  不会出现「半迁移状态被当成已完成」。

## 四、什么时候会拒绝运行，怎么办

| 情形 | 界面表现 | 出路 |
|------|----------|------|
| 数据比程序新（降级打开了新版书稿） | nf_api 启动即退（退出码 2），日志写明原因 | ① 升级到新版程序；② 回退数据快照 |
| 迁移链有缺口（改了结构却没登记步骤） | 同上 | 补一个 `Step`，或把数据回退到对应版本的快照 |
| 某一步执行失败 | 同上，报错点名是哪一步 | 修好后重跑；或整体回退快照 |

拒绝是**刻意**的：拿旧代码去写新书稿，坏的是用户唯一那份数据；停在这里至少还留着
完整快照与未推进的版本戳。

## 五、承诺边界（如实声明）

- **承诺**：书稿要么被迁到当前结构、要么被明确拒绝，**不存在「静默写坏」这条路**；
  每次真迁移都有快照与回退命令。
- **不承诺**：跨大版本的数据结构永久兼容。结构该改就改，改了就登记迁移步骤 ——
  这是这套机制存在的意义，不是它的失职。
- 快照只覆盖 `snapshot.SNAPSHOT_ITEMS`（progress / setting / outline / chapters /
  summaries / merged）。`config/` 与 `materials/` 的回退靠归档机制，别拿快照当整仓备份。

## 六、给维护者：改数据结构时必须做的四件事

1. `scripts/utils/workspace_migrate.py` 的 `DATA_SCHEMA` **+1**；
2. 在 `MIGRATIONS` 里加一个 `Step(from_v, to_v, fn, title, safe=…)` —— 两处不同步，
   `status()` 会大声拒绝（版本链断裂），不会静默跳过；
3. 回归里加一条真跑该步骤的断言（参考 `tests/unit/test_workspace_migrate.py`）；
4. 发布说明写清「这版会把你的书稿从 vX 迁到 vY，回退点在哪」。

自检：`python tests/unit/test_workspace_migrate.py`（48 断言，含「步骤被静默跳过」
这类反面用例 —— 该缺陷在机制的第一版就被它当场抓住过一次）。
