## 一、一票否决项（4 条）

### 否决 1｜三条 fail-closed 叠加，出厂态报告为空（对应第 6 条：需求没有可成立的验收标准）

| 项 | 内容 |
|---|---|
| **问题** | 方案把"缺材料"一律处理成"不出结论"，且缺的材料在 P0 内不可获得。三条叠加后，10 章里至多 2 章能得到档位，其余 8 章落「不可判定 A」，报告主体为空 |
| **证据** | ① `_requirements_spec` R15 AC-15-6「阈值缺失 → 不可判定 A：阈值未定」；② 同文件 §八「本期不填数值（缺值一律「不可判定 A」）……**缺陷段占比阈值**」；③ R05 AC-05-1「缺卡 → 报"口径不完整"，**该判据结论不得出具**」；④ R18 AC-18-2 能力证据区要求"不漏 + 不误报双向"，而 R19 基准集当前为空（AC-19-4 只能写"误报率未标定"）；⑤ `_interaction_spec` 头注与 A21 断言的是 0/8/2 分布 |
| **后果** | ① 三档中「需定点重写」与「可开始逐字改」都需要"缺陷段占比阈值"，该阈值缺席 → 只有第 1、2 章能靠章级依据落「需重写本章」（AC-24-5），其余 8 章无档位；② 交互卡 A21「不得出现可以开始逐字改」会因"根本没有档位"而**空过**（假通过）；③ 报告首页的 `0/8/2` 总账无法生成，I1 首屏第 2 区域缺失。**P0 唯一交付物（报告）在出厂态不成立** |
| **处置（建议）** | 把原则写死进 PRD 业务规则：**缺材料只降可信度，不阻结论**。允许阻结论的原因码只保留两个：A=输入/口径缺失、B=对象链断裂（即 R15 已有的两个码）。具体三处：①"缺陷段占比阈值"必须由作者在 R04 登记表录入（建议初值 20%，录入即生效，可按 R06 重判），**不得留空**；②AC-05-1 改为"无卡 → 该条判据标『未解释』，结论照出并标注"；③R18 的"无基准集"只降证据等级，不阻报告出具 |
| **若不解决** | P0 结项时手里没有报告，只有一份"不可判定"清单。这是比"报告说稿子不行"更差的交付物——**用户会正确地判定这一期什么也没做** |

> 横切观察：R05/R15/R18 三条同型（缺材料→不出结论），说明方案在"防止假绿灯"上用力过猛，把 fail-closed 用成了 **fail-empty**。假绿灯的反面不是空报告，是**带可信度标注的报告**。

### 否决 2｜R01 验收线与事实基线算术冲突，照实现会推出错误的系数（对应第 6 条）

| 项 | 内容 |
|---|---|
| **问题** | AC-01-4 要求"stage6(4000) 对 2186 字必须判不足"。事实基线已明确 stage6 本次**不是**被预算削的，且在 4000 token 容量内 |
| **证据** | R01 AC-01-4 原文：「真实配置下 stage5(8000) 对 5967/6058 字、**stage6(4000) 对 2186/1967 字必须全部判不足**」；`_product_facts` §三-6 二次校正：「实测 refined 1812–2252 字**低于** 4000 token 的容量（约 2800–3000 中文字），说明本次差异……**不是预算卡住**」；同文 §三-6 采用的换算为「6000 字 ≈ 8000–9000 token」（系数 1.33–1.5），需求 §八 给的参考区间为 1.3–1.6 |
| **后果** | 要让 2186 字被判不足，须满足 `4000 < 2186 × 系数 × 安全系数`，即乘积 > 1.83。取系数 1.5、安全系数 1.2 时乘积 1.8 < 1.83 → **断言为红**；取 1.6×1.2=1.92 → 断言为绿，但同一系数下大量"目标 2000 字"的合法场景会被误判不足。**验收线把实现推向一个偏严的系数，而这个系数与事实基线自相矛盾** |
| **处置（建议）** | AC-01-4 改为「stage5(8000) 对 5967/6058 字；**stage6(4000) 对 5967 字**（即 stage5 修好后的真实输入）必须判不足」。2186 字应作为**反例**写进同一 AC：「2186 字在 4000 token 下必须判**足够**」——这才是能区分"校验真的在工作"的双向断言 |
| **若不解决** | 要么断言永远红（无法交付），要么为了让它绿而把系数抬到误伤合法场景的水平，**R01 从防线变成新的误报源** |

### 否决 3｜"当前稿"在三份文档里有三个值，状态机"已过期"无判定基准（对应第 11 条：核心业务对象状态流转矛盾）

| 项 | 内容 |
|---|---|
| **问题** | 章节稿这个对象在 P0 有 raw/checked/refined 三个版本，"当前稿"未定义，三份产物各指一个 |
| **证据** | ① `_interaction_spec` 头注：「第 3 章**现为 2186 字**，它的原稿曾有 5967 字」；② 同卡 I5 步 2：「稿子里第 3 章 **2183** 字，成品里 2186 字」；③ 同卡 I5 差异说明：「现在稿子里的第 3 章：**5967** 字；成品里的第 3 章：2186 字」；④ R07 AC-07-2 把它写成「`refined/03`=2183 与 `raw/03`=5967 不一致 → 必须报「成品与源稿不一致」」——**用 refined vs raw 冒充 成品 vs 源稿**；⑤ `_product_facts` §三-6 表：03 章 raw 5967 / checked 2186 / refined 2183 |
| **后果** | ① 若"当前稿"取 raw → 每章恒过期（评审本来就会改字），"已过期"失去信息量，作者两周内学会忽略该徽标；② 若取 refined → 03 章 2183 vs 成品 2186 仅差 3 字即报「判定不可信」，是标点级的假警报；③ R08 的 4 条 AC、AC-15-4（03 章不可判定 B）、R16 三元组**全部压在这个未定义字段上**，R08 只有 4 条断言却是本期地基 |
| **处置（建议）** | 在 R08 增加一条硬定义并全卡替换：**`current_version` = 该章最新已落盘版本（refined 优先 → checked → raw）**，且此字段是 R07/R08/R15/R16 的唯一输入。raw↔成品 的差异归 R02（三稿对照），**不得**作为"过期"依据。交互卡三处数字统一为 `current=2183 / 成品=2186 / raw 曾=5967` |
| **若不解决** | AC-07-2 与 A14 会同时"通过"而语义错误——**这是本项目最不能接受的一种通过**（一次新的、发生在验收层面的假绿灯） |

## 三、评审会会被问到的 12 个问题

| # | 问题 | 建议答案 |
|---|---|---|

## 五、与竞品的对照判断

> 数据来源：`docs/roadmap-2026Q4.md`（2026-10-20 两轮实查）。**该台账自述其信息来自 README／文档／截图，未读源码（§丙 明写"不看源码文件"）**，因此以下对照为**文档级**，不足以支撑"护城河"结论。

| 同类 | 台账记录的质量能力 | 与本次"判定能力"的等价物 |
|---|---|---|
| 书童 Pagekin（GPL-3.0，1.7k★） | 审稿报告逐条勾选 + 修稿逐段对比 | **形态上有部分等价物**：逐条勾选≈I2 裁定，逐段对比≈I6。是否有"引不上原文即作废／确定性判据"【需调研验证】。→ **"逐条勾选 + 逐段对比"不是护城河** |
| 催更姬（MIT，33★） | 讨论式，无结构化判据 | 无等价物（按其自述） |
| ainovel-cli（MIT） | 叙事深化（Arc）、指南针、step checkpoint、审美维 | "审美维"是模型生成型评分，不是确定性判定；无"定位到段句 + 不可判定"机制。等价物弱【需调研验证】 |

**判断（三层，分开说）**：

1. **不是伪需求**。痛点有实测（判据判合格 10/10、作者判垃圾 10/10），不是凭感觉提的。三家同类中没有记录到"确定性判据 + 引不上原文即作废"的等价物。
2. **是不是护城河：【需调研验证】**。roadmap §乙 把"可验证的质量"列为护城河，但这是**自评**，对照对象只读到 README 级。至少三项须核实：①书童的逐条勾选是否要求原文引用；②它的审稿报告是否由模型生成（若是，则同为"被考核方自评"，我们的差异成立）；③是否有"不可判定"这一档。
3. **更尖锐的一层：即使是护城河，它也不可迁移**。判定能力的价值来自"口径被标定到作者本人的口味"，而标定劳动与标定数据都不可随安装包迁移。对新用户来说，他遇到的第一道墙是**字数**（现有闸门已拦），不是"判据说合格而实际是垃圾"——**那个痛只在"已经跑通了 47 次"的重度用户身上出现**。所以本能力对外是"回访用户功能"，不是"获客功能"。对外发布时应按此定位写文案，不要写成"我们的 AI 写得更好"。
4. 许可证红线已合规登记（GPL-3.0 只抄机制不抄代码），本次不新增风险。

### 6.2 砍掉的每条为什么不破闭环

| 砍/降 | 为什么不破闭环 |

### 6.3 若你认为应扩：加一条

**R15 增一列「先改这 3 处」。** 理由：P0 的交付物是报告，而报告当前只回答"能不能用"，不回答"下一步干什么"。加一列（按规则权重 × 命中次数排序）+ 一个离线预测（"改完这 3 处，该章档位从"需重写本章"变为"需定点重写""），成本约等于一次排序加一次重算，直接对治"跑了没意义"这个判断。这不是新需求——它是 R14/R15 已有数据的另一种排序。

### 6.4 P0 完成时的一句话交付声明

> **这一版做了两件事：给已经写完的 10 章出了一份能指到"第几段哪一句"的不合格清单（全程离线、零花费），并解除了三处替你做写作决定的提示词锁。**
> **它没有让稿子变好——效果验证在下一期。它也没有能力证明自己不误判——那取决于你导入一份自己觉得合格的稿。**

（三条禁止表述：不得说"质量提升"、不得说"已解决 AI 腔"、不得说"判定能力已成立"——最后一条的准确说法是"判定装置已就位；不漏已有证据，不误报未标定"。）
