## 一、端型矩阵与现场条件

### 1.1 端型矩阵（一端，不扩）

| 端 | 定位 | 谁 | 现场条件 | 承担任务 | 为什么必须在这一端 |
|---|---|---|---|---|---|
| **Windows 桌面（Electron + 本地 Python 引擎）** | 唯一的作业台 | 作者本人（非程序员，同时是唯一开发者） | 单人单机、数据全本地、断网也要能跑、可能一次跑数小时、可能中途关机/断电 | S05 章纲勾选、S07 读两章否决、S08 判读评审、S12 判定能否进精修、S14 改标准后重判、S15 找"哪句不行"、S09 打回重写 | ① 判定要**与原文并置**，需要能同时摊开"缺陷清单 + 原文 + 评审前后对照"三块，手机做不到；② 终态是 Word 逐字精修，Word 在桌面，中间夹一层手机等于把稿子搬两次；③ 判定全离线零 token，本地引擎随包安装，没有服务端可以依赖 |

### 1.2 不做的端（明确排除）

| 端 | 排除理由 |
|---|---|
| Web | 唯一使用者就是本机；上 Web 等于凭空引入服务端、账号、上传稿件三件事，与"数据全本地、断网可跑"直接冲突 |
| 移动 / 平板 | 判定结论必须与原文句子同时可读，手机上只能二选一；且写作者的真实动作（逐字改）在 Word，不在手机 |
| 大屏看板 | 没有观众、没有指挥中心、没有汇报场景；一个人的判定不需要远距可读 |
| 小程序 / H5 | 无分享、无传播、无免安装需求（已装 NSIS 包） |

### 1.3 三条推论（这三条决定后面所有页面写法）

1. **交付动作必须在界面内闭环。** 判定、重判、重出、导出四个动作各自在所在页签内有一个按钮可点。报告页不允许出现"请在命令行执行"或"请联系开发者"；只允许"点这里再看一次"。凡做不到的，改成"这个动作本期没有"。
2. **长任务必须有落点。** 单机跑数小时 + 可能断电 ⇒ 每个长动作必须能回答三件事并在界面上显示：上次跑到哪、现在还在不在跑、断了下次从哪接。禁止"任务已提交，请稍后查看"这类无落点提示。
3. **只有一端，所以风险不是跨端不同步，而是端内两处显示打架。** 现有 `progress.json` 会把 8/10 章标 done，而报告结论是 0/10 可用。**界面只允许一个结论来源**：凡与报告结论冲突的旧标记，一律要么被覆盖显示，要么显式加前缀"旧标准下"。这条是 I1/I4 的硬约束。

### 2.2 为什么不新增页签（四条）

1. **判定是章节的属性，不是独立工作场所。** 把判定单拉成页签，作者看结论时看不见原文，必须来回切 —— 这正好违背本阶段第一目标"一眼看出哪句不行"。
2. **新增页签 = 状态面积翻倍。** 每个页签都要独立定义加载/空/失败/部分成功等 7 类状态，6 个新页签就是 6 套状态要维护，而单用户产品没有并发收益。
3. **既有 13 页签是按流程阶段切的，不是按信息切的。** I3 属章纲（已在分章）、I6 属审稿（已在审稿）、I5 属交付（已在导出）—— 每个落点都有现成主人，无一需要新家。
4. **导航深度要给键盘效率让路。** 73 处待改要逐条裁定，如果每条裁定要跨页签，等于每条多两次点击。

### 2.3 端内去重（对应"两端各做一套"的等价风险）

单一端不存在跨端冗余，但存在**同一结论两处显示**：
- 允许显示"结论"的地方只有 I1（整本/逐章档位）与 I5（成品是否过期）。I2/I3/I4/I6 一律**只读引用**结论，不得各自重算。
- I4 重判完成后，I1 刷新；「流水线」页签与「章节」页的旧"已完成"字样由 I1 的结论覆盖显示，或被强制加前缀"旧标准下"。

### I5 成品失效提示与重出

| # | 区域 | 首屏必须可见 | 内容 |
|---|---|---|---|
| 1 | 成品卡片 | ✅ | 文件名 + 出自哪一版 + 出的时间 + **「已过期」徽标** + `第 3 章已更新，成品还是旧的（10-25 16:00 出的）` |
| 2 | 凭据（两行，同屏） | ✅ | 字数：`现在稿子里第 3 章 5967 字，成品里只有 2186 字`；时间：`第 3 章 10-27 改过，成品是 10-25 16:00 出的` |
| 3 | 这意味着什么 | ✅ | `你手上这份 Word 里的第 3 章，是被评审压过两次的那一版，不是你现在盘上的稿` |
| 4 | 动作 | ✅ | `重新生成 Word 成品`（本期禁用 + 灰字`本期没做：重写的那章要真跑模型，会花钱`） / `打开成品所在文件夹` |
| 5 | 不做什么 | ✅ | `这份成品不会被自动覆盖` |

> **分期口径（主理人 2026-10-28 已裁，不再是待裁项）**：F10 的 P0 形态 = **成品与源稿一致性检测**（字数比对 + 时间比对 → 标"已过期" + 给凭据），**不做自动重出**；重出留 P1。
> 理由（写进卡里）：P0 的硬验收是「零 token、断网可跑」。重出必须重跑评审 → 润色 → 成书，会破这条线；而"能看见成品已过期"是纯离线比对，正好是本期能给的。
> **失效判定必须给凭据**：至少两项（源稿字数 vs 成品字数、源稿改动时间 vs 成品生成时间）。只给一个"已过期"徽标 = 未实现。本次实证：`第 3 章 5967 字 / 成品 2186 字`、`第 3 章 10-27 改过 / 成品 10-25 16:00 出的` —— 作者拿到的是被压缩两次、且不是最新源稿的那一版。

### 6.1 概念 → 作者视角说法（界面上一律用右列）

| 内部概念 | 界面说法 | 备用（更长的解释，用于悬停/帮助） |
|---|---|---|
| 判据 / 判定规则 | **合格标准条目** | "这条是在查什么" |
| 口径 / 口径版本 | **合格标准（第 N 版）** | "这一版是 2026-10-26 定的" |
| 缺陷 / 缺陷单 | **要改的地方** | "这一章有 7 处要改" |
| 三档结论 | **可以开始逐字改 / 要定点重写 / 要重写本章** | 三档固定，不许改写成别的词 |
| 独立事件 | **推进故事的事** | "让人物处境、他知道的事、关系、目标里有一个变了" |
| 伪具体 | **空转的句子** | "看着很具体，其实读完什么也没变" |
