## 一、产品是什么

### 1.1 形态
- Electron 桌面客户端（Vue 3 + 自写 CSS，7 个前端依赖）+ 本地 Python HTTP 服务（`scripts/nf_api.py`，默认 8765）
- 主界面为**页签式**：项目 / 分章 / 章节 / 校对 / 判定 / 设置（+ 使用手册）
- 主操作模型为**八阶段流水线**：

| 阶段 | 做什么 | 产物 |
|---|---|---|
| 1 | 设定（人物/地点/势力） | `data/setting/setting.json` |
| 2 | 全书大纲 | `data/outline/global.md` |
| 3 | 分章章纲（核心事件/涉及角色/功能/钩子） | `data/outline/chapters/NN.md` |
| 4 | **正文写作** | `data/chapters/raw/NN.md` |
| 5 | 逻辑检查 | `data/chapters/checked/NN.md` |
| 6 | 润色 | `data/chapters/refined/NN.md` |
| 7 | 合并 / 转 docx（支持用户 Word 模板） | `output/` |
| 8 | 收尾（判定报告、导出） | `output/judge_report.md` 等 |

### 1.2 规模
- 后端端点 **213 个**（域模块 `scripts/nf_api_domains/*.py` 路由表 + `nf_api.py` 内联 elif 去重）
- 界面有调用的 **190 个**，**无任何入口的 23 个**（复验命令见 5.6）
- MCP 工具 **33 个**（`scripts/nf_mcp.py`），供外接 Agent 调用
- 单元 + HTTP 测试 **172 个用例**（`nfctl test`）；e2e 视觉验收 **157 条断言**（`tests/e2e/e2e_ux_verify.py`，不在 `nfctl test` 内）
- 判定引擎规则 F01–F05，**零 token 确定性检查**

### 1.3 真正的资产（规划时不要当作可抛弃的旧代码）

【事实】以下四项在同类产品中没有找到同等深度，且都已有实现和测试：

1. **上游结构化能力**：设定集（人物/关系/traits/locked）→ 大纲 → 章纲（核心事件列表）。有 schema 单一事实来源 `utils/setting_schema.py`、正典快照 `/setting/canon`、冲突检测 `/setting/conflicts`。
2. **零 token 判定引擎**：句长/字数、可替换骨架句、章纲密度、落点、12-gram 复读、元话语比例、段落结构。这些是规则不是模型调用，成本为零、可离线、可反复跑。
3. **Obsidian 知识库接入**：多库（一次一个生效）、每库排除项、只读不写用户的库。
4. **外接 Agent 工具面**：33 个 MCP 工具，含读正文、发起审查、提案、提问通道。

## 二、用户的约束（这一节最贵，全部是原话）

### 2.1 定位
> "产品定位是通过'代写''让我写得更快'。"

> "AI全流程都做，人收尾。AI能拿出一份勉强能看的版本（真人一半水平）都算了不起。毕竟自己训练模型甚至当模型供应商成本太高。"

**由此确定的硬约束：**
- 形态：**AI 跑完全流程，人只做收尾**。不是"人写 AI 辅助"，也不是"边写边介入"。
- 质量目标：**"真人一半水平"就算成功**。不是"写得好"。
- **不允许自训模型**，不允许自建模型服务。只能用现成 API / 订阅模型。

### 2.2 速度
> "不用证明，就是快。人写撑死了一天两万字（十小时），AI一两天给你整本书几十万字。"

**这意味着"速度"不是待验证的假设，是产品定义的一部分。** 任何增加人在场时间的改造都与定位冲突。

### 2.3 用户的真实痛点（三句原话，按他提出顺序）
> "用户控制不了写作，用户看不到写作，AI在瞎写，用户根本什么都做不了。"

> "实际上如果界面上什么都点不了，等于功能不存在。东西全在agent黑箱里。"

> "我觉得根本不是那么简单的问题，难道不是整个客户端和交互模式都需要深入改造吗？"

### 2.4 用户的写作基准（决定验收标准）
> "全世界AI写的我都读不下去，我甚至想过自己训练写作专精AI。全世界的AI现在在写作领域都很垃圾。绒花墨坊已经属于把垃圾的质量提升几千倍了。"

**注意这条的内部张力**（规划必须处理，不是忽略）：
- 相对基线：从"完全不可读"提升到"能看一点" = 巨大进步
- 绝对判断：仍然"读不下去"
- 两者可以同时为真。**因此任何"跑一章让用户读一读判断好不好"的验收方式都失效**——那个判据永远不会亮。

### 2.5 对投入的判断
> "钱必须花在规划上，选择大于努力。今天选好了，明天节约100亿token。"

用户愿意为规划投入大量 token，**前提是规划能给出方向选择，而不是执行计划**。

## 三、已查证的技术事实（可复验）

### 3.1 写作过程对用户不可见（这是"看不到"的物理原因）
`scripts/stage4_writing.py:1002`
```python
def _on_piece(piece):
    if piece:
        _ch_state["chars"] += len(piece)   # 只取长度，piece 的文本被丢弃
```
- 流式回调**收到了正文分片**，但只累加字数，**文本从不落盘、不流到界面**
- 界面因此只能显示"已写 1200 字"（`console/src/App.vue:2274` 附近读 `current_chars`）

### 3.2 生成单位是"章"，中途无法介入
`scripts/stage4_writing.py:4` 注释：“每章一次独立子会话”。
- 一次调用产出整章（数千字）
- 中途唯一动作是**停止**，而停止 = 半截不入稿 = 白跑（`_run_task_stream` 的语义）
- 人的动作只有两个：接受，或整章重来

### 3.3 界面上没有入口的能力（23 个端点）

第一次扫描报 57 个，是正则只认单参写法（`call("GET","/x")` 全漏），修正后 23 个。**请用 5.6 的命令自行复验**。

其中【判断：这几项对"人能否干活"影响最大】：

| 端点 | 能力 | 现状 |
|---|---|---|
| `/plan/*`（**8 个全部**） | 提案四态：propose / list / get / select / write / drop / revive / stats | 界面零入口；**但 MCP 已暴露 propose + list** |
| `/setting/canon` | 正典事实快照 | 无入口 |
| `/kb/search` | 知识库检索 | 只有 Agent 能用 |
| `/chapters/verify` | 正文退化校验 | 结果界面看不到 |
| `/auto_rewrite/run` | 自动重写（自评低分触发） | 只能命令行跑 |
| `/prompts/get|list|save` | 提示词读写 | 待确认（可能被动态拼接绕过扫描） |

**这造成一个具体的荒诞状态**：AI 能提案（MCP 有 `nf_plan_propose`），提案落进 `data/state/` 下的文件，**界面看不见，人也无法选择/采纳/丢弃**。即"AI 提了案，人不知道"。

### 3.4 数据模型不支持"高效修改"【判断，但缺口本身是事实】

| 缺口 | 事实 | 后果 |
|---|---|---|
| 段落无稳定标识 | 正文是纯文本 `data/chapters/*/NN.md` | 改动无法追踪、无法做回归、无法判断"改这处影响哪里" |
| 设定无时态 | 只有当前快照（`setting.json`），无"第 N 章结束时的事实状态" | 第 20 章无法校验"他这时知不知道那件事" |
| 无伏笔账本 | 有 `/foreshadow` 端点，界面无入口（待复验） | 埋了什么、欠几条回收，无法自动核对 |
| 无改动影响分析 | —— | 改第 5 章的一个决定，第 12/18 章是否失效，系统不报 |

### 3.5 判定引擎只测下限
- 覆盖：字数/句长、可替换骨架句、章纲密度、落点、12-gram 复读、元话语、段落结构
- **不覆盖**：perplexity（AI 约 10–30，人类 40–100+）、burstiness（句长**聚簇**分布，非平均值）
- 因此"判定合格" ≠ "读得下去"，用户可能觉得"合格但没劲"，这不矛盾

### 3.6 近期改动效果未验证
- `prompts/stage4_writing.md` 于 0.7.28 从 3240 → 5909 字符，加入叙事技术要求（场景三问、展示不讲述、具体压倒抽象、感官预算、节奏、对白潜台词、AI 腔禁令）
- **效果未经验证**（用户尚未在真实章节上确认）
- 文风注入：`book.style_rule` 为空时不注入风格块；`book.style_reference` 指向 `materials/style_sample.md`，**该文件在当前仓库不存在**

## 四、同类产品的机制（已查证，供规划参照）

| 产品 | 生成单位 | 人的介入点 | 上下文机制 |
|---|---|---|---|
| **NovelAI** | 逐段（paragraph-level）续写 | 随时打断、改、继续 | Lorebook + Memory |
| **Novelcrafter** | scene beat → 正文 | 每个 beat 后停 | Codex（别名/关系/提及追踪） |
| **Sudowrite** | ~300 字 × 多候选 | 选中任意段落 Rewrite/Expand/Describe | Story Bible |
| **Revise** | 全文 | 修订模式，**逐条接受/拒绝** | 无故事圣经 |
| **Reedsy** | 按幕 | **锁住**好的幕，只重生成坏的 | 结构框架 |
| **绒花墨坊** | **整章** | 写完才能看；只能整章重写 | 设定集 + 滚动摘要 + 上一章尾 |

一条被反复引用的判断（来源：第三方评测）：
> "一次性生成器的界面在说：模型的输出就是成品，作者的角色是接受或拒绝。那不是编辑控制，那是语法更好的老虎机。"

【判断，可能错】但注意：**这条批评直接指向"边写边介入"的解法，而用户已明确要"AI 跑完、人收尾"**——所以不能照抄 NovelAI/Sudowrite 的形态。参照点应该是"**收尾工作台**"，同类产品里没有直接对应物（Revise 的修订模式最接近，但它是短篇/单文档形态）。

## 六、未决问题（真正需要规划者回答，我答不了）

按依赖顺序：

**6.1 收尾时长怎么分解？**
产品唯一的优化目标应该是"从 AI 交稿到可交稿，人花多少小时"。但这个数**没有测过**。需要拆成：找问题 / 判断该不该改 / 动手改 / 改完担心改坏，四段各占多少。
> 没有这个数，所有优化都是盲的。

**6.2 "真人一半水平"怎么量化？**
用户说"勉强能看"就算成功。需要把它拆成可测阈值：事实矛盾数、AI 腔密度（perplexity/burstiness 分布）、读不通句数/万字、每章推进度。
> 这是验收标准的全部。定不出来，产品就没法验收。

**6.3 段落级锚点怎么设计？**
既要稳定（人改动后仍能认出"这是同一段"），又不能污染正文（作者看到的是干净文本）。这是"可修改结构"的地基。

**6.4 设定时态模型怎么做？**
要记录"某章结束时的事实状态"（谁知道了什么、谁在哪、伤好了没有），且**不让作者维护成本爆炸**。这是长篇一致性检查的前提。

**6.5 改动影响如何传播？**
改一处会影响哪些地方，哪些必须报警、哪些可以忽略。误报多了作者就会关掉它——这个阈值怎么定。

**6.6 八阶段里哪些该砍？**
如果目标是"整本快点能交"，有些为"单章更好"服务的工序价值要重算。

**6.7 界面该以什么为单位组织？**
现在是 6 个功能页签 + 213 个端点。是否改为按"人的动作"组织（看现状 / 定方向 / 改稿 / 交稿）？这四个工作台是否成立？

**6.8 30 万字规模下的一致性怎么验证？**
需要的不是"这一章对不对"，是"整本 30 万字有没有互相矛盾"。这是纯工程问题，但规模带来的复杂度未知。

## 七、不要基于以下说法做判断

1. **不要信"底层能力都有"** —— 23 个端点界面无入口，能力在界面之外等于零。用户原话："界面上什么都点不了，等于功能不存在。"
2. **不要信"测试 172 全绿"** —— 测的是后端；e2e 157 条测的是**现有页签结构**。两者都不证明"人能把一本书做出来"。
3. **不要信"0.7.28 改了提示词就会好"** —— 未验证，且用户的验收基线是"AI 文本一律不可读"。
4. **不要假设用户会逐步介入写作过程** —— 他要 AI 跑完、人收尾。任何要求人在生成过程中持续在场的方案都与定位冲突。
5. **不要按"短篇工具"的形态设计** —— 30 万字长篇的连续性、伏笔、设定时态，是短篇工具不解决的问题，也是本产品唯一可能建立壁垒的地方【判断】。
6. **不要相信"用户会自己创造答案"** —— 用户原话："这是你（和其他规划AI）需要解决的问题，不是等我来创造答案。" 但同时也说"我心中有模糊的预想"。**方向要他确认，方案不能要他给。**
