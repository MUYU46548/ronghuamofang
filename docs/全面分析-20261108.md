# 绒花墨坊 · 全面分析（2026-11-08）

> 触发：作者的原话 ——“改这么点东西太小了，整个项目需要大量重改（这种大改已经至少六七次了），
> 同类那么多哪怕整个仓库克隆过来都不会这么差，抄东西都不会抄。”
> 本文只回答三件事：**已经有什么、还缺什么、为什么改了六七次还是这样**。
> 结论先说：**不该有第 8 次大改**；该把一条线做穿（见第七、八节）。

## 二、已经做出来的（按能力，不按提交）

### 2.1 管线（这是它的主体）

- 七阶段：素材归并 → 整体大纲 → 逐章大纲 → 逐章写作 → 逻辑检查 → 润色 → Word；另有阶段 8 Markdown 导出。
- 断点续跑、单阶段重跑、失败重试、打回（清下游）、人工跳过、整轮快照。
- 章范围（阶段 4/5/6 只跑几章）、每章字数区间、全书字数目标。
- 止烧：token 累计/单次上限、熔断后暂停、界面上看得见用量；金额阈值在订阅通道上无效这件事也写明了。
- 成本账本 `logs/runs.db` + 成本报表（按阶段、按轮次、按供应商）。

### 2.2 self 引擎（零 token，只出任务书）

- 阶段 1~6 各出任务书，外部执行方写完重跑即续；判完成只看盘上产物。
- 派单记账 `data/state/self_dispatch.json` + 越界检测（任务书只派 1 章却写满全书会被点名）。
- 按钮级派单（本周）：大纲精修、整章重写、提精修、段落重写 → 任务书 + 草稿 + 采用。

### 2.3 判据体系（它最独特、也最重的一部分）

- 判定引擎：口径表 J1–J22、三档结论（可逐字改 / 定点重写 / 重写本章）、缺陷单、事件勾选、逐句裁定。
- 七维评审账本：每条结论必须引原文，引不中不算分。
- 结构六项：问号占对白、连续单回合问答、角色句长差、极短独立段、对话段占比、平均段长。
- 其他确定性检查：AI 腔病灶词扫描、设定引用过期、索引与实物对账、字数口径（只数汉字）、标点归一。

### 2.4 编辑与改稿

- 编辑器三模式：编辑 / 阅读（点名看设定卡）/ 段落批注；三层稿切换（原稿 / 检查稿 / 润色稿）。
- 审阅台三栏（左章列表、中正文、右本章出场+本章大纲+七维）。
- 段落级：候选 → 改前/改后并排 → 采用；段落历史与回退；手改保存（带“除目标段外逐字节不变”硬校验）。
- 整章：重写、重跑（按范围）、多写几版择优、残稿接管。

### 2.5 知识库

- 多库同时读、同名冲突点名（当前库优先）、**按库各配一套五类目录**（本周）、库本体只读红线、沙盒审核队列。

### 2.6 接入与安全

- HTTP 251 个端点；MCP 白名单工具 + stdio 垫片；Agent 模式守卫（审批/打回/归档/建项目/改正文/改止烧 一律 GUI-only）；审计日志。
- 导出：Word 模板占位符、目录域、Markdown 导出、成稿保真核对（剥内部注释、字节比对）。

### 2.7 工程底座

- 230 个用例文件、release-check 一条命令跑全套、质量门、界面文案黑话审计、提示词出厂副本、打包与产物核验。

## 三、还缺什么（诚实分级）

### P0 · 缺的是“改”这条路，不是功能

| 缺的 | 现状 |
|---|---|
| 行内指令（选中一段 → 说一句 → 就改） | 只有“选中段落 + 右侧输入框 + 让 AI 只改这一段”，藏在批注态 |
| 停下来说话 | 审批门只给“确认 / 打回”；打回是整阶段清下游，太狠 |
| 意见沉淀（说了要记住） | **完全没有**：这次说的要求，下一章不生效 |
| 章级“带意见重写” | 接口有（提精修），入口在校对页，没人找得到 |
| 章级版本树 / 一键撤销 | 有段落历史、有章节备份，但没有“这一章的时间线” |
| 判定完直接动手 | 勾完只给结论，动作在别的页签 |

### P1 · 按钮还在“不可用”

运行审查（缺 `review_report.json` 的 schema）、批量精修、自动重写、语义审稿、开局方案 / 写作方向候选、重跑本章（self 语义未定）。
这六个的共同点不是“没写代码”，是**没有定“怎么判它做完了”**。

### P2 · 没验证过的

安装版真机五条（安装/多库/酒馆/判定/卸载重装）、段落两栏的目检截图、去 AI 腔基线数、字数真跑、自动更新（未接）、出厂预设真机跑一本。

### 明确不做（写在这里免得反复讨论）

再加生成类功能、引 UI 框架、多库自动合并、把去 AI 腔做成出章硬门。

## 四、为什么六七次大改都没解决

**因为六七次改的都是“界面怎么排”，不是“人怎么改稿”。** 66 个界面提交里，93% 是重排、加面板、分组、换配色。

### 4.1 数据模型和工作模型对不上

- 工作模型：**一章文本 + 一句话**。人说“这段太拖”，就要看到这段变了。
- 数据模型：**阶段产物 + 状态机 + 账本 + 口径 + 快照 + 归档**。
- 中间没有一层“工作副本”（草稿/候选）—— 本周才补上，而且只补在段落上。

任何界面动作都要穿过五层：进度状态、阶段产物、下游作废、账本、快照。于是每次改交互都变成“加个面板”。

### 4.2 判据替代了判断

项目把“能证明”当成“能做”。J1–J22、七维、六项结构指标 —— 这些能证明“这章不能过”，
但**不能把一章变好**。作者要的是“改”，判据给的是“考”。

判据越多，越像一个考试系统，而不像一个写作工具。

### 4.3 停下来的位置错了

停在**阶段边界**（2 和 6），因为那是“要不要继续烧钱”的位置；
人需要停在**这一章、这一段**，因为那才是“这句话不对”的位置。

### 4.4 上帝组件让每次改动只能“加法”

`App.vue` 8,900 行、`nf_api.py` 4,855 行。任何一条新交互都要在上帝文件里开一个分支，
于是最省事的做法永远是**再加一个面板**，而不是改现有的那一屏。67 次之后，就长成了现在这样。

### 4.5 测试给的是虚假安全感

5.6 万行用例锁的是：端点接上了、枚举一致、文案没有黑话、路由表对齐。
**没有一条用例问“作者能不能用三步改掉一句话”。**
所以“全绿”和“烂爆了”能同时为真 —— 这不是测试写错了，是测试测的是内部自洽，不是可用性。

### 4.6 文档治理代替了代码治理

AGENTS.md 50 KB、docs 39 篇，靠写纪律弥补抽象缺失（“这个函数不许那样子用”）。
文档越厚，说明代码越没有稳定的结构；而新人（或下一个 agent）读文档的时间，比读代码还长。

## 五、“哪怕克隆一个同类仓库都不会这么差” —— 这句话对在哪

同类项目（SillyTavern、NovelAI、彩云/汤圆那类写作助手）的交互核心只有四样：

1. 一个**文本域**（不是七阶段产物）；
2. **版本**（每次改动留一版，可回退）；
3. **行内工具**（选中就有：改、扩、缩、换语气、删）；
4. **撤销栈**（Ctrl+Z 就够）。

它们的数据模型三张表就能装下。**模型简单，交互才敢做深。**

墨坊抄了它们的**功能名**（角色卡、酒馆导入、段落批改、多写几版、候选择优），
但没抄**交互**（就地浮层、即时撤销、版本树、一句话指令）。
因为抄功能只要加接口，抄交互必须动数据流 —— 而它的数据流是为“无人值守批量跑”设计的。

这就是为什么“克隆一个仓库会更好”：人家的复杂度花在编辑器上，这个仓库的复杂度花在状态机上。

## 六、我的判断：不要第 8 次大改

理由不是怕麻烦，是**前 7 次的模式已经很清楚**：大改 = 2–3 天重排界面 + 一批用例改断言，
交付时“看着新”，用起来还是“读一章要五次点击、改一句要换页签”。

第 8 次大改会得到同样的结果，因为**改的还是排布**。

真正需要的是**一条线做穿**：读 → 说 → 变 → 看到差 → 撤销。只做这一条，其他的先不动。

## 七、只做三件（建议）

| # | 做什么 | 为什么是它 | 估时 |
|---|---|---|---|
| 1 | **行内指令浮层**：选中文字（或光标所在段）→ 浮出输入框 → 三个动作（改这处 / 重写这章 / 往后都这样） | 这是“像编辑器”的分水岭；现在这些动作散在三个页签 | 2–3 天 |
| 2 | **每章版本树 + 一键撤销** | 没有它，任何自动改动都不敢用；段落历史已有，缺章级时间线 | 1–2 天 |
| 3 | **意见沉淀（两个作用域）** | 让“说过的话”下次生效；没有它，每章都要重新说 | 1 天 |

范围只有这三件，**不新增页面、不重排页签、不删任何功能**。
入口就放在已有的审阅台（左章 / 中正文 / 右栏），右栏加“我说一句 + 三动作 + 两个作用域勾”。

## 八、验收怎么算过（可量化，别再拿用例数糊弄）

1. 改一句话 ≤ **3 步**（选中 → 说 → 采用），且中途不换页签；
2. 打开即读当前章 ≤ **2 次点击**；
3. 撤销一次 ≤ **1 次点击**，且能看到“改前/改后”；
4. 说出的一条“往后都这样”，**下一章必须体现**（用一条用例证明它被注入）。

这四条过不了，就别说“改好了”。

## 九、方寸这条链（用户点名：它的能力还是没出现）

我这边能看到的方寸工具共 **32 个**：建卡、改状态、写/读日志、计划、验收门、用量上报、检索。
**没有“派给谁、等结果、回填”这三件** —— 全是账本动作。

所以“方寸派活”这条链现在不存在；派活仍然只有两条路：
① 你复制提示词给人/AI；② 墨坊自己的 `nf_dispatch_task`（拉起 Hermes 子会话）。

要补，只有两种改法：

- **方寸侧加两个工具**：`dispatch_task(target_agent, brief)` + `poll_task(id)`，并规定回执写回哪张卡；
- **墨坊侧做“任务书目录 + 完成回执”**：任务书落盘即登记，外部写完写一个 `.done` 回执，方寸只读目录。

两边都不做的话，“从方寸外面绕”是唯一的实际状态 —— 这不是我的偏好，是账本没有那只手。

## 十、下一次交付的清单（我现在就能做）

1. 行内浮层 + 三动作（复用已有的段落候选 / 提精修 / 任务书接口）；
2. 章级版本树 + 一键撤销；
3. 意见沉淀（`writing_notes.json` + 两个作用域 + 注入）；
4. 补一张段落两栏的真机截图（这周做的东西还没目检过）。

做完这四件再谈“重构”；在这之前，任何“大改”都只是第 8 次重排。
