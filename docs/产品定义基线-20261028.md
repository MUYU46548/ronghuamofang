## 零、先看这一页

### 一句话诊断

**系统能产出「结构合规、字数不达标、通篇 AI 腔」的稿，而全部判据都判它合格——验收权在模型手里，不在你手里。**

不是写得少，是没有任何一环有权说"这稿不行"。

### 六条根因（全部可定位到文件行）

| # | 根因 | 位置 |
|---|---|---|
| 1 | 验收权在被考核者手里：模型自写 `<!-- quality: 8/10 -->`，系统按 ≥6 收稿 | `stage4_writing.md:86` / `stage4_writing.py:828` |
| 2 | 字数判据不是产出闸门：只在断点续跑时筛"要不要重写" | `stage4_writing.py:835` |
| 3 | 口径变更后存量不重判：10-26 下限 2000→5000，8/10 章仍标 done | `progress.json` / `validation/01.json` |
| 4 | 风格规格写死在默认档位：7 条极简派规格，无范文也照给，不可关闭 | `prompts/style/narrative_style.md` |
| 5 | 密度上限被锁死：「可补充细节，但不得新增关键情节」 | `stage4_writing.md:19` |
| 6 | **评审环节销毁正文**：要求回抄全文但 `max_tokens: 8000` 装不下 6000 字 | `stage5_check.md:39` |

### 第 6 条是最致命的，也是"太弱"的机械原因

| 章 | raw（stage4 写的） | checked（stage5 后） | refined |
|---|---|---|---|
| 03 | **5967** | **2186** | 2183 |
| 05 | **6058** | **1967** | 1969 |
| 01 | 1960 | 1961 | 1812 |

**写 6000 字 → 评审压回 2100 → 断点续跑判"不足 5000" → 重写 → 再压。** 死循环。而 `finish_reason` 是 `stop` 不是 `length`，既有截断防线完全拦不住。

**更深一层：伪具体是 token 稀缺下的最优解。** 预算不足时，细节比情节便宜——写两个事件会让每个都仓促，写一个事件把它拆细最省 token 又"看起来有质感"。所以「十次呼吸之内落不了章」不是模型的审美偏好，是预算逼出来的解。

### 一期的赌注（明示，避免误读）

P0 交付的是**"一个能判死的系统"**，不是"一本更好的书"。

- 交付：判定报告（哪章不行、哪句、为什么、第几段）+ 三处提示词锁已解除 + 口径可版本化重判
- **不交付**：更好的稿。拆锁的效果要真机才知，推到二期，且需你另行批准跑模型
- 为什么这么切：你已明确「再跑试跑意义不大」，而拆锁效果无法离线证明。先把"能判"做实，才有资格谈"能写"

## 一、业务界定

### 1.1 服务对象

使用者即作者：长篇小说作者、非程序员；同时是唯一开发者与产品负责人（一人三身份）。交付对象是**对外发布的产品**（MIT、已有 NSIS 包）。

| 能做 | 不能做 |
|---|---|
| 点 GUI；读自己的书判断"能不能用"；Word 逐字精修；在自己产线上写实现 | 跑命令；读代码识别"假绿灯"；把研发与使用分给两个人 |

**三条推论**：① 作业必须 GUI 内闭环（契约原话「用户永远不会用终端，包括我自己」）；② 以"你去跑一下验证"结尾的验收等于没做；③ 没有第三方，**系统是唯一的质检人**。

### 1.2 业务问题

现状流程（《潮汐档案》真机全链，2026-10-25）：

| 步 | 工序 | 谁判定合格 | 实际 |
|---|---|---|---|
| 1–3 | 素材归并 → 总纲 → 章纲 | 人工审批门 | 通 |
| 4 | 逐章写正文 | **模型自填分数** | 10 章 done，1968–2796 字 |
| 5 | 七维评审 + 审美五问，**同时改稿** | **同一模型自评** | 均分 8.14、`complete: true` |
| 6 | 润色 | 无闸 | 通，字数再降 |
| 7–8 | Word 合成 → 归档 | 无闸 | 56KB docx，全书 24,189 字 |
| 9 | 你精修 | 你 | 读两章即停，判"垃圾" |

**不解决会怎样**：这条循环已被实测重复 47 次 run（10-17 ~ 10-27，done 17 / failed 12）。跑完 → 读两章 → 判"太弱" → 说不出弱在哪 → 去加功能。**换模型不解，因为根因 4、5、6 都在提示词与预算里。**

### 1.3 业务价值

| 指标 | 定义 | 当前基线（实测） | 目标 |
|---|---|---|---|
| 一次性可精修率 | 一次全链跑后你判"可直接进精修"的章占比 | **0/10** | 待确认 |
| 字数达标率 | 过下限的章占比 | **0/10** | 待确认 |
| 单章推进量 | "改变故事状态的事件"数 | **1 事件/章** | 下限 2（已定） |
| 判据可信度 | 系统判"合格"而你判"垃圾"的章占比 | **10/10（全背离）** | 待确认 |
| 精修工时/改动率 | 逐字精修一章净耗时、改动字数比 | **需你实测 1 章** | 待确认 |

**纪律**：不得用"重写率改善"表述（契约⑥件二红线）；模型自评分不得作为价值证明。

### 1.4 产品边界

**做**：夺回验收权 / 让判据成为闸门 / 给"伪具体·AI 腔"可核对清单 / 口径版本化与存量重判 / 评审与改稿分离。

**不做**：游戏文案通道（负向边界已钉死）、多 Agent 自主调度、500 章无人值守、平台文风预设、云端账号与发布闭环。

**一期不做**：v0.8–v0.10 全部（写作中干预、逐章验收开关、角色关系网、去 AI 腔改写器、读者视角审稿、Skill 导入、作品级预设）——它们都预设"稿已够用"；长篇规模优化；模型换代适配；**不接受"再跑一次出厂预设"作为验收**。

## 三、产品定义

### 3.1 能力架构（四层）

| 层 | 回答什么问题 | 缺了会怎样 |
|---|---|---|
| **L1 作者决策层** | 哪些判断系统无权代做（事件数认定、感受裁定、验收放行） | 系统会用自己的标准冒充你的标准 → 根因 1 复发 |
| **L2 判定能力层** | 这稿能不能用、哪句为什么不能用 | 你只得到"太弱"两个字，说不出弱在哪 |
| **L3 口径治理层** | 按哪一版标准判的？标准改了旧结论还算数吗 | 口径一改，旧认定仍为真 → 根因 3 |
| **L4 生成侧解锁层** | 哪些锁必须拆、怎么证明真拆了 | 判定做得再好，稿子仍是同一腔调 |

四件事的落点：**事件粒度 → L1 + L4（章纲）｜AI 腔 → L4（风格档位）+ L2（可核对清单）｜判定口径 → L3｜审批门 → L1**。

### 3.2 三项能力（P0 交付物）

| 交付物 | 功能 | 零 token 可验 |
|---|---|---|

| **B 拆锁** | F15–F17 | ✅ 确定性断言 + 会失败的反证 |
| **C 口径闭环** | F08–F10（含存量重判、成品一致性） | ✅ 手动一键重判 |

## 四、需求规格

29 条需求（R01–R29），P0 = R01–R24。完整版见 `03-需求规格.md`。此处只列**会决定成败的六条**。

| R | 需求 | 验收（可判定） | 反证（会失败的形式） |
|---|---|---|---|
| R01 | 预算—篇幅联动校验 | 全文回抄型阶段执行前，`max_tokens ≥ 目标字数 × 系数 × 安全系数`，不满足即拒跑并报"预算只够装 N 字" | 造 max_tokens=4000 + 目标 6000 字 → 必须拒跑；删掉校验则复现"输出 1800 字 + `finish_reason=stop`" |
| R02 | 正文销毁检测 | 三稿对照列出字数差与逐句 diff；缩减 >5% 标"疑似销毁" | 5967 字 03 章必须报「5967 → 2186 → 2183，成品取自被压缩两次的版本」 |
| R11 | 章纲密度虚高识别 | 第 1 章必须报此项 | 删掉章纲一条事件后重跑，仍报此项或**同时**报 R12 → 失败 |
| R12 | 正文未落地章纲识别 | 删事件版必须报此项；原稿不得报 | 原稿报此项 → 失败 |
| R22 | 拆锁③ 默认不注入风格规格 | 无风格档位下 `{{style_rules}}` 渲染为空，**不含那 7 条任何一条** | 把默认改回 narrative 档 → 断言必须红 |
| R15 | 三档结论 | 10 章只落在"需定点重写/要重写本章"两档，**不得出现"可开始逐字改"**（基线 0/10） | 人为补足字数与句长后重判，档位必须变化 |

### 状态机修订（解决两处缺陷）

| 缺陷 | 修订 |
|---|---|
| 质量分由被考核方填写却作升级依据 | 升级依据改为**判定记录 + 作者裁定**，且记录必须带三元组：**稿件版本 × 口径版本 × 判定结果**。模型自评分降级为"参考信息"，不进任何状态迁移 |
| `已成书` 后改章，成品是否失效无定义 | 明确：改章即把成品标「已过期」，并记录"源稿字数 vs 成品字数 / 源稿时间 vs 成品生成时间"两项证据；重出走 P1 |

### 权限（单用户，但需要 actor 字段）

无多角色、无越权面。但存在两身份：施工位（改口径）与作者位（下判定/勾选），R04/R13/R16 的记录必须带 `actor` 字段，否则二期无法回答"这条标准是谁改的、这个拒收是谁定的"。

## 五、交互定义

**端型：只有 Windows 桌面一端**（Electron + 本地引擎），不做 Web / 移动 / 平板。六处界面全部落在**既有 13 个页签内**，零新增顶层页签。完整版见 `04-交互定义.md`。

| 编号 | 界面 | 落点 | 首屏必须可见 |
|---|---|---|---|
| **I1** | 判定报告（整本一页） | 章节页签新增分区 | 一行总账（`10 章：0 可以开始逐字改 · 8 要定点重写 · 2 要重写本章；全书 73 处要改`）+ 章节表（每行前 3 处段号与短引）+ **固定串「存量回测判定，非新跑拦截」「本报告不改变现有成品文件」** |
| **I2** | 章节判定详情 | 从 I1 进（≤2 层） | 「这章有 7 处要改 · 已判 3/7」+ 左侧缺陷清单（每条两行：`第 3 段 · 换数字照样成立`）+ 右侧原文标句 |
| **I3** | 事件清单勾选 | 章纲页签 | 「这一章发生了几件事（你来定）」+ 四类必选 + 系统只报"疑似凑数" |
| **I4** | 标准设置与变更重判 | 设置页 | 改前先看影响面：`按新标准：2 章达标（原 8 章）` |
| **I5** | 成品失效提示 | I1 横幅 | 「成品已过期：第 3 章已更新，Word 还是 10-26 的」+ 两项证据 |
| **I6** | 评审结论与修改痕 | 章节页签 | 三份对照：原始稿 / 意见 / 改了什么 |

### 文案纪律（进界面的词必须是作者能看懂的）

| 禁用 | 替代 |
|---|---|
| 判据 | 标准 / 这条规则 |
| 口径版本 | 第几版标准 |
| 管线、stage、落盘、幂等、闸门、门禁 | 不出现 |
| F 编号、S 编号、R 编号 | 不出现 |

### 三档结论（措辞沿用你的原话，不引入新词）

`✓ 可以开始逐字改` / `⚠ 要定点重写（第 11、24 段）` / `✕ 要重写本章`，并附病因四选一：章纲密度虚高 / 正文没写章纲里的事件 / 评审时被删短了 / 润色时又删短了一次。

## 六、评审意见

| # | 修订 | 理由 |

| 1 | **F18b 拆成"修 + 守"**：先静态改 `stage5_check.md` 8000→25000、`stage6_polish.md` 4000→15000，再加预算校验 | **评审原话：只拦不修，P0 之后主流程会硬停。** 从"跑出垃圾"变成"跑不了"更糟。调预算是零成本静态改动，且不修则拆锁的效果无从谈起 |

### 6.3 关于"P0 是否过载"

评审判定为**范围风险而非失控**（24 条中真正独立的工作面只有 4 个：规则引擎 / 报告 / 口径治理 / 拆锁），但指出成本排序错了——18 条验收是"界面上存在某字符串/某按钮禁用/某字段非空"，全是界面工程量，与"零 token"无关。

**本基线的处理**：不砍条目，改用交付顺序对冲——**I1 + I2 先出（让报告能看）→ 规则引擎后补（让结论更准）→ 口径治理 → 拆锁**。理由：一个能看的报告 + 语料不够多的规则，比一套完美规则 + 看不见的报告更能让你判断"这一期有没有用"。
