# B3 · 知识库“多库同时生效”：先把数据模型摆出来（2026-11-07）

> 试跑原话：“知识库貌似只支持单个库，我记得提过多个库，没做吗？”
> 卡片 `task-20261104-011` 要求“先摆数据模型给你拍板”。**这份文档就是那个提案，代码未动。**

## 一、现状核实（先纠一条：不是“没做”）

| 能力 | 现状 | 证据 |
|---|---|---|
| 登记多个库 | ✅ 有 | `GET/POST /config/vaults`（书签存 `vaults.json`，每库各自带 `skip_dirs`） |
| 逐个切换当前库 | ✅ 有 | `POST /config/vaults/switch`，换库不动任何笔记文件 |
| 每库独立排除项 | ✅ 有 | 切回来还是上次勾掉的那几个目录 |
| **同时读多个库** | ❌ 没有 | `_vaults_public()` 里写死 `model: "single"` |
| **界面说明“同时只有一个生效”** | ✅ 已有 | 设置 → 知识库 →“我的库”那一行明确写着“同一时刻只有一个生效” |

**结论**：卡片里的“反证（界面上看不到这句话 = 未完成）”**已经满足**。真正剩下的只有一件事：
**要不要支持 B 模型（多库同时读）**。

## 二、两种模型，差别只在“扫描面”

### A 模型（现状）：单库生效

```
当前库 = vault_path（system.local.yaml）
扫描面 = [当前库] - 它的 skip_dirs
切换库 = 改 vault_path（其它库仍在书签里，不参与扫描）
```

- 优点：**来源唯一**。同名条目不会打架，“这条设定来自哪个库”永远确定。
- 缺点：跨库写作时要来回切；两本书共用一套世界观时无法同时读。

### B 模型（提案）：多库同时读

```
启用库 = [库1, 库2, …]（各自带 skip_dirs 与 enabled 开关）
扫描面 = 所有启用库的并集
冲突   = 同名条目出现在多个库 → 按下面的判据处理，并**在报告里点名**
```

改动清单（只列要动的地方，不含 UX 打磨）：

| 位置 | 要改什么 | 风险 |
|---|---|---|
| `vaults.json` | 每项加 `enabled: true`，顶层加 `model: "multi"` | 低（老文件缺字段 → 按 A 模型兼容） |
| `utils/setting_schema.py` | `vault_path` 单值 → `vault_paths` 列表（保留单值读法做兼容） | 中（几乎所有读 `vault_path` 的地方要跟着改，有漏改就“只读一个库但界面说读了两个”） |
| `obsidian_bridge` / `kb_index` | 扫描从单根改多根，路径归一化要防跨库同名目录 | 高（这是真风险点） |
| 冲突判定 | 见下节 | 中 |
| 界面 | 每库一个启用开关；顶部写清“现在同时读 2 个库”；冲突条数点名 | 低 |

## 三、如果上 B，冲突怎么定（这是必须先定的口径）

同名条目（同一个角色/地点/概念来自两个库）有三种可选判据 —— **必须选一个，不能“看情况”**：

| 判据 | 语义 | 代价 |
|---|---|---|
| **① 主库优先**（推荐） | 书签里位置靠前的库赢，其余只在报告里列为“被覆盖” | 用户要理解“顺序即优先级”，界面上要有拖拽/上移按钮 |
| ② 时报错并要求人工 | 冲突条目不进检索，报告点名，等用户处理 | 最保守，但每次加库都可能中断写作 |
| ③ 全部合并进上下文 | 同名条目都带上 | 上下文膨胀 + 模型看到两条互相矛盾的设定（最差） |

推荐 **① + 报告点名**：与“设定引用过期”“判定引擎”同一套价值观 —— 机器摆事实，作者决断。

## 四、需要你拍板的三件事

1. **要不要 B 模型**？（A 已够用的话，这条直接关单，只保留现状说明）
2. 若上 B：冲突判据用 **① 主库优先** 吗？
3. 若上 B：**默认全开还是默认只开当前库**？（建议默认只开当前库 + 明确提示“还有 2 个库没启用”，
   避免“加了库就悄悄改变写作输入”）

## 五、不建议现在做的理由（我的判断）

- 现在真书跑的是 **单库**：工作区 `vault_path` 只有一个，多库属于“将来可能用到”的能力；
- B 模型的主要风险不在开关，而在**扫描多根带来的路径归一化与同名冲突**；
  这块一旦写歪，症状是“检索到的设定来自错的书”，而界面一切正常 —— 属于最贵的那类缺陷；
- 现阶段投入产出比更高的仍是：**真跑一本 12 章验证字数闭环**、B4 阶段 2（面板骨架）。

如果两条都用不上，建议把这张卡关掉，把“多库”记进 `docs/agent` 的已知边界里。


## 六、拍板与落地（2026-11-07 晚）

作者原话：“**多库同时生效 B（多库一起读），用户本来就可能不止一个库。**”
所以上面“四、需要你拍板的三件事”按这个口径定了：

| 问题 | 决定 |
|---|---|
| 要不要 B 模型 | **要**，且作为默认 |
| 冲突判据 | **① 主库优先 + 报告点名**（当前库即主库） |
| 默认全开还是只开当前库 | **默认全开**（加入书签即参与）；每库留 `enabled` 开关 |

落地清单（都已实现，用例 `tests/unit/test_vault_multi.py` 25 条）：

| 位置 | 改了什么 |
|---|---|
| `config` | 新增 `obsidian.vault_model`（`multi` 缺省 / `single` 退回旧行为），写 `system.local.yaml` |
| `vaults.json` | 每项新增 `enabled`（缺省 true）；**当前库永远参与**，不许停用 |
| `obsidian_bridge` | 新增 `get_vault_model()` / `get_vault_roots()` / `scan_vault_multi()`；`scan_vault()` 加 `skip_dirs`/`tag_root` 两个入参（单根调用零变化） |
| `utils/kb_index` | `build_index` / `recall` 接受多根列表；每条注明 `root`/`rel`；同名条目去重进 `skipped_same_name` |
| stage4 | 通道 A 走 `scan_vault_multi()`，通道 B 传多根；同名冲突在日志里点名一次 |
| API | 新增 `POST /config/vaults/enable`、`POST /config/vaults/model`、`GET /config/vaults/scan`（零 token 体检） |
| GUI | “我的库”显示“同时读 N 个”、每库启用/停用、切模型、检查同名冲突（冲突逐条列“用 A 的、忽略 B 的”） |
| 手册 | `console/src/help/04-vault.md` 改写成多库口径（含“为什么同名不让系统自动合并”） |

**仍然保留的边界**（如实写，别假装更强）：
- 五类目录映射（角色/地点/势力/概念/年表）仍**全局一套**，不按库区分；
  两个库结构不同时，以当前库的结构为准。
- 非当前库的条目路径带库名前缀，因此 **`sync_diff`（库 ↔ 已导入设定集对账）刻意只扫当前库**：
  导入设定集是单库整体替换语义，把辅库条目混进来只会报出一堆假“缺失”。
  写作注入、locked 检查、审稿一致性对照则都走多库。
