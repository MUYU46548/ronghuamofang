## 一、批量派单（核心机制，替换"一次一条"）

### 1.1 为什么必须批量

**[码]** 每次模型调用都是一个独立的 `dsh --profile headless` 子进程（`dsh_client.py:591`，
timeout 1800s）。单条派单 = 一条批注花掉一次完整 agent 回合的时间。
40 段一章、每段一条批注，就是 40 次冷启动 —— 你说的"50 分钟过去了"是这么来的。

**[码]** 而且"批"这件事已经有现成骨架：审稿页的 `review/batch_refine` 就是
"把 decisions.json 里的 N 条决策攒好 → 起一个 job → 一次跑完"。缺的不是机制，是**让它成为默认路径**。

### 1.2 五步流程（界面按这个顺序设计）

| 步 | 在哪 | 用户看到什么 | 动作 |
|---|---|---|---|
| ① 收集 | 正文页（右栏） | 一条条"批注"：章号 · 段号 · 原句片段 · 一句话意见 · 来源判据 | 加进待改清单 / 划掉 |
| ② 筛选 | 待改清单 | 按章分组；每条可单独勾选是否本次派单 | 勾/不勾，排序，批量删 |
| ③ 派单确认 | 抽屉（覆盖在正文上，不换页） | 四块：改哪些 / 影响面 / 预计成本 / 风险 | 派单 / 再改改 |
| ④ 执行 | 队列（右栏常驻） | "正在算：第 12 章 8 条 · 已 3 分钟" | 可取消（真杀进程） |
| ⑤ 回收 | 待改清单变成"待裁定" | 每条：改前 / 改后 / 字数差 / 来源 | 逐条采纳或丢弃；整批可撤销 |

**关键**：①到⑤不换页。你说过"改一句话 ≤ 3 步"，批量版是"改 20 句 ≤ 5 步"。

### 1.3 派单确认页必须有的四块（这是你点的名）

| 块 | 内容 | 数据从哪来 |
|---|---|---|
| 改哪些 | 按章分组的条目表：章 · 段 · 原句前 20 字 · 意见 · 来源 | 待改清单 |
| 影响面 | 涉及 N 章 / M 条 / 预计改动字数区间 / 会一起改不可拆的条目 | **新的**：需要按条目算预计字数（可用原段字数 × 系数） |
| 预计成本 | token 区间 + 预计耗时区间 + **依据标签**（历史均值 / 字符折算） | **[码]** 复用 `scripts/estimate_tokens.py`：历史优先（`logs/runs.db` 的 cost_log），无历史按 1.5 字符/token 兜底，且它已经能输出 JSON 给 API 用 |
| 风险 | 跨章批次会整体失败；超 `budget.token_limit` 会停；DSH 无 max_tokens 旋钮，长批可能被截断 | 配置 + 现有闸门 |

你说"预估成本极难"—— **不难，八成的基建已经在**。真正难的是"准"，所以界面上必须
把估算**标成区间并写依据**，不写单一数字。UI 上就一句：
"预计 8–14 万 token（依据：本书阶段 4 历史均值）/ 约 6–11 分钟"。

### 1.4 批次上限（先给经验值，L2 实测再调）

- 单批 ≤ **15 条批注**
- 单章 ≤ **8 条**
- 超过 → 界面自动拆成两批，并说明"第 13–20 条排到下一批"

理由：DSH 没有输出预算旋钮（`max_tokens_knob=False`），批越大越可能被截断，而截断 = 整批作废。
15/8 是保守起点，**不是结论**，L2 第一轮实测后要写成判据。

### 1.5 与现状的差距（L2 要补的）

| 现状 | 缺口 |
|---|---|
| **[码]** `paragraph/preview` 单条、`paragraph/pending` 列单条候选 | 缺"一批条目一次派单"的入口 |
| **[码]** `review/batch_refine` 批量，但对象是审稿 finding，不是正文批注 | 形态对、对象不对；要么扩它，要么照它的形状新开一个 |

## 四、多书（S15=B：一次只开一本，不乱就行）

**[码]** 现状：`data/books/` 下已有两本（`示例书名（待填写）`、`雾港核心`），
`switch_book.py` 也在。多书**不是从零做，是补规则**。

"不乱"= 三条硬规则：

1. **同一时刻只有一本是"当前书"**，存在工作区配置里，所有页面读同一个值。
   任何页面都不许自己记住"我刚才在看哪本"。
2. **换书是显式动作**，且**待改清单/派单未收口时不许换**（先收口或明确放弃），
   否则批次会落到别的书上。
3. **书名重名**：书目录由书名派生（`data/books/<书名>/`），重名就撞目录。
   规则二选一，等你定（进第二批问卷）：

| 方案 | 行为 | 代价 |
|---|---|---|
| A 自动加后缀 | `雾港核心-2`，提示"同名已存在，用这个名" | 用户可能真以为改成功了，两个名字长得太像 |
| B 拒绝并要求改名 | 直接说"已有同名书，请换一个" | 多一步，但永远不会出现两本近似的书 |

我的倾向是 B：书名是唯一标识，自动改名的账后面算不清。
