# 转向书：从“写书流水线”到“读改工作台 + 判据库”（2026-11-17）

> 触发：暮雨“改不改都无所谓，改随时能改，现在是整个项目要大转向”。
> 本文只定方向与取舍，不排工期；凡是与本文冲突的旧文档（产线/路线图/旧 roadmap）以本文为准。

## 一、旧定位（放弃）

**小说生产流水线产品**：8 个阶段、17 个页签、自己造“调模型”的那一层、自己维护 Electron 壳与安装包。

它的问题不是做得不好，而是**解决的是“跑”**；而“跑”不是他的难事（不靠墨坊也已经跑完几本），
“改”才是。继续在这条线上投入 = 继续优化一个不是瓶颈的东西。

## 二、新定位（一句话）

**墨坊 = 把 AI 写出来的东西改到能读的工作台 + 给 AI 干活时用的硬判据库。**

两件事，只有两件：

1. **读改**（人的活）：逐段读、按批注改、候选并排比、采用/回退、改完有没有回到线内 —— 界面就是产品。
2. **判据**（机器的活）：字数（只数汉字）、退化、文风四指标、节级、判定三档、口径表、Word 出口 —— 以工具形态供任何 agent 调用。

## 三、形态：寄生工作台（推荐 A）

| 形态 | 是什么 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐）** | 墨坊做**DSH 插件**：读改面板以 Web 页形式挂在 DSH 里；业务仍是墨坊本地 HTTP | 重写读改面板的前端；放弃 Electron 壳 | 宿主漂移（用“薄壳 + 业务在后端”限损） |
| B | 保留 Electron，但只留 3–6 屏读改面板 | 最低，可立刻做 | 仍是两个应用，裁决台与工作台割裂 |
| C | 纯工具包（无界面），读改靠 DSH 对话 + 文件 diff | 最省 | 逐段对比、逐条勾、看 diff 这些场景在聊天流里做不动 |

选 A 的理由：工作台该由宿主提供，不该自己造；而“判据与读改”是墨坊的独有价值，做成插件页刚好。
C 不可行：横向对比与逐条勾选是“改”的核心动作，聊天流承载不了。

## 四、死掉的东西（明确停工，别再回头维护）

- **阶段推进 UI**（一键工作流 / 全自动 / 步骤条 / 审批门界面）：改由 DSH 会话与方寸卡驱动
- **17 页签导航**：收窄到读改面板（章节 / 批注 / 候选 / 历史 / 判定 / 导出）
- **成本页、进度页、收件箱页**：这些是账本视图，DSH 的工具返回就能给
- **自建“多轮迭代”叙事**（讨论构件、成书提炼的 UI 部分）：模型侧交给宿主
- **按版本的界面发版节奏**：只随插件能力发版

## 五、活下来的东西（资产，不可丢）

- 判据与闸：`verify_chapter` / `judge` / `structure` / 口径表 / 字数口径 / 退化检测
- 三层稿与后悔药：`raw/checked/refined`、`history/`、`para_history/`、`rewrite_backup/`、`truncated/`
- 段落候选机制：`preview → para_pending → apply（冲突不覆盖）→ drop`、批注状态机
- 提示词库：`prompts/stage*.md`（尤其段落精修、去 AI 腔、节级写法）
- Word 出口：模板 + 15 项模板校验
- 工作区数据形态：一本书 = 一个目录，这对任何宿主都成立

## 六、第一步（零成本，且能立刻否证）

把“改一章”的最小面板清单化，并在 DSH 插件形态里做一个**只读原型页**（不接真数据）：

- 清单（按一次改章的真实动线）：① 章列表与三层状态 ② 正文 + 段落定位 ③ 批注列表 ④ 候选并排 + diff ⑤ 采用/回退 ⑥ 改完的判据回执
- 原型的验收不是好不好看，而是两条：**改一处要几次点击**、**改完能不能一眼知道还要不要再改**

## 七、不可谈判的三条

1. 书的账本不进方寸（暮雨已否）。
2. 判据只做硬闸，不做提示词劝告。
3. 每个改动都要回答：它让“逐章读改”更快、更准、更可回退吗？不是 → 不做。
