# 转向书：从“写书流水线”到“读改工作台 + 判据库”（2026-11-17）

## 2026-11-17 追加定案：形态改 **B**（保留墨坊界面，DSH 当内核）

作者：“选 A 不如直接吃整个 DSH 当内核，B 如何？但也不用只留 3–6 屏吧？几乎全都能留。”

据此定：

- **形态 = B**：保留墨坊现有 Electron 界面（17 页签几乎全留），**不重写进 DSH**；
  DSH 只当**内核**（执行层），通过 `engine: dsh` 被调用。
- **A（做成 DSH 插件页）降级为备选**：只有在“宿主成为瓶颈”（例如多设备、单一入口变成硬需求）时才重提。
  理由：界面是**已验证资产**（327 条界面用例、56 张截图全绿），把它重写进 rc 阶段宿主 = 拿验证换未验证。
- **“几乎全留”的解释**：页签留，但**功能冻结**——除读改链以外不再加新功能；
  账本类页签（成本/进度/收件箱）保留为只读视图，不再迭代。
- **墨坊不写 DSH 专属逻辑**：引擎保持三选一（direct / hermes / dsh），换谁都不改业务。
- 继续投入的唯一方向仍是读改链（批注 → 候选 → 采用 → **判据回执**）。

> 触发：作者“改不改都无所谓，改随时能改，现在是整个项目要大转向”。
> 本文只定方向与取舍，不排工期；凡是与本文冲突的旧文档（产线/路线图/旧 roadmap）以本文为准。

## 一、旧定位（放弃）

**小说生产流水线产品**：8 个阶段、17 个页签、自己造“调模型”的那一层、自己维护 Electron 壳与安装包。

它的问题不是做得不好，而是**解决的是“跑”**；而“跑”不是他的难事（不靠墨坊也已经跑完几本），
“改”才是。继续在这条线上投入 = 继续优化一个不是瓶颈的东西。

## 二、新定位（一句话）

**墨坊 = 把 AI 写出来的东西改到能读的工作台 + 给 AI 干活时用的硬判据库。**

两件事，只有两件：

1. **读改**（人的活）：逐段读、按批注改、候选并排比、采用/回退、改完有没有回到线内 —— 界面就是产品。
2. **判据**（机器的活）：字数（只数汉字）、退化、文风四指标、节级、判定三档、口径表、Word 出口 —— 以工具形态供任何 agent 调用。

## 三、形态：寄生工作台（已定 B，A 降为备选；见文首追加定案）

| 形态 | 是什么 | 代价 | 风险 |
|---|---|---|---|
| A（备选） | 墨坊做**DSH 插件**：读改面板以 Web 页形式挂在 DSH 里；业务仍是墨坊本地 HTTP | 重写读改面板的前端；放弃 Electron 壳 | 宿主漂移（用“薄壳 + 业务在后端”限损） |
| **B（已定）** | 保留 Electron 现有界面（几乎全留），DSH 只当内核 `engine: dsh` | 最低，且不丢已验证界面 | 仍需自己维护壳与打包 |
| C | 纯工具包（无界面），读改靠 DSH 对话 + 文件 diff | 最省 | 逐段对比、逐条勾、看 diff 这些场景在聊天流里做不动 |

选 B 的理由（2026-11-17 定）：界面是已验证资产，重写进 rc 宿主等于拿验证换未验证；
而“跑”这一层交出去即可，不必连界面一起交。A 留作宿主真成瓶颈时的备选。
C 不可行：横向对比与逐条勾选是“改”的核心动作，聊天流承载不了。

## 四、死掉的东西（明确停工，别再回头维护）

- **阶段推进 UI 继续迭代**（一键工作流 / 全自动 / 步骤条 / 审批门界面）：入口保留，但不再加功能；
  生产流程改由 DSH 会话与方寸卡驱动
- **17 页签导航**：形态 B 定案是**几乎全留**（不删页签）；但除读改链以外**功能冻结**，
  账本类（成本 / 进度 / 收件箱 / 讨论 / 成书提炼）保留为只读视图，不再迭代
- **成本页、进度页、收件箱页**：保留现状可查，不再扩字段、不再做新图
- **自建“多轮迭代”叙事继续扩充**（讨论构件、成书提炼的 UI 部分）：保留现状，不扩；模型侧交给宿主
- **“界面重写进 DSH”的节奏**：形态 B 下墨坊仍随 Electron 包发版（0.9.x）；
  `dsh-novelforge` 插件走自己的版本线，两者不互相绑

## 六、第一步（零成本，且能立刻否证）

## 附录 A · 旧入口逐条结论（P2 #10，2026-11-17）

判据只有一条：**它让逐章读改更快、更准、更可回退吗？** 不是 → 停更入口（不删代码、不再加功能）。
下表按页面实际入口逐条落结论；“标 △”的三条需要作者拍板（影响的是“还要不要这个方向”，不是代码风险）。

| 入口 | 对“逐章读改”的作用 | 结论 |
|---|---|---|
| 章节 → 审阅台（编辑器 / 段落批注 / 候选 / 采用 / 历史） | 就是读改本体 | **继续投入**（本轮 P1 全落在这里） |
| 精修（段落级工作台） | 同类动作的第二条路 | **保留**，已改称“直接改正文”并写明与候选流程的差别；不再扩功能 |
| 判定 / 校对 / 文风 | 回答“改完有没有回到线内” | **保留只读**（判据库的地基） |
| 大纲 / 分章 | 服务“跑”，不服务“改” | 保留只读，冻结迭代 |
| 素材 / 设定 | 给改稿提供上下文（设定卡点名有用） | 保留现状，不迭代 |
| 成本 | 账本视图 | 保留只读，不加字段 |
| 收件箱 | 待办入口 | 保留只读 |
| 项目（换书 / 归档） | 低频但必要（一本书 = 一个目录） | 保留，不再扩 |
| 导出（Word / Markdown） | “改完要能交出去” | 保留（15 项模板校验不弱化） |
| 流水线（一键工作流条） | 服务“跑”，与“改”不同族 | 入口保留，**冻结**；生产交给 DSH 会话与方寸卡 |
| 讨论（多轮叙事） | 与“改”同类，但成本高、判据弱 | **继续投入（作者拍板 A）**：下一步把讨论结论落成批注（带段号与来源） |
| 多写几版（Best-of-N） | 花钱换质量，与读改链正交 | **继续投入（作者拍板 A）**：已补结构六项证据；下一步按段落版 |
| 沙盒（回写设定库候选） | 只在“改设定”时有用，且永不写 vault | **继续投入（作者拍板 A）**：下一步做设定冲突预检（只读、零 token） |
| 成书提炼 | 把写完的书变正典，不是逐章读改 | **继续投入（作者拍板 A）**：CLI/GUI 都留；下一步做分章摘要检索 |

**停更的含义**：不删代码、不动数据，只停止在界面上加功能 / 改版式；哪天判据答案变了，解冻即可。
